# 问题 1：生成的英文词少且重复（重构 scene_word 生成流程）

> **实施后记（2026-08-23 晚，真机验证）**：本节方案经三轮迭代落地为 **V4.2**，最终架构与下文设计有差异，以本后记为准：
>
> 1. **V4（LLM 标注英文词）真机失败**：qwen2.5:7b 无法稳定完成"写故事+标注"元任务（每篇仅标 3~4 词且编造词表外的词），印证 V3 注释的教训。已回退为"模型只写纯中文故事 + 代码全池注入"。
> 2. **两段式生成**：新增"选词阶段"——先让 LLM 从 120 词池中挑选 targetCount+3 个适合主题的词（简单选择任务，遵从度高），故事阶段把选中词的首义项**内联进要求正文**（"必须全部出现：宝藏、小路…"）。实测内联小清单遵从度接近 100%，长列表自由发挥则很低。
> 3. **隐藏根因修复（重要）**：词库释义带词性前缀（如 `n.餐馆`、`vt.饮 vi.喝 n.饮料`），旧 splitMeanings 切出的义项含 `n.` 前缀，injectFromDict 在正文中永远匹配不到 → 这正是**最初"英文词太少"投诉的隐藏根因之一**。现已剥离词性标记后再切分。
> 4. JSON 解析加固：qwen 偶发把 segments 拆成多个数组（`}],[{`），解析前做粘连修复。
> 5. 真机实测（4 主题 × 本地 qwen2.5:7b）：成功率 4/4，词数 9~14，篇目间词汇差异明显。
>
> 最终代码流程：buildWordList（主题词30+随机补足120）→ pickWordsFromPool（选词+3余量）→ buildPrompt（内联必用清单）→ injectSegments（全池注入+自写英文词补标签，义项已去词性前缀）→ acceptOutput（≥8）→ 重试≤3。

## 根因回顾（详见问题分析报告）

1. `NARRATIVE_WORDS` 固定词列表每次无条件进候选池 → product/market 每篇必现
2. 候选池实际只有 ~20 个词，注入依赖"代码扫描中文释义"，命中率不稳定 → 词少
3. （V4.2 新发现）词库释义的词性前缀（n./vt.）导致大量义项注入匹配失败

## 关键源码事实（决定方案形态）

- **渲染器高亮依赖英文词在文本内**：`scene-word.renderer.ts:15` 的 `highlightWords` 用 `\b` 正则在 `seg.text` 中高亮英文词；产品核心体验是"中英混杂文案 + 词汇高亮"。**因此最终 text 必须含英文词**，纯中文故事 + 仅标签是不够的。
- **V3 重构结论仍成立**（content.service.ts 头注释）：qwen2.5:7b 写纯中文故事最稳，让它直接写中英混杂或做复杂元任务不可靠。所以采用"模型标注 + 代码定向注入"折中。
- **`randomWords` 的隐藏行为**（cet.service.ts:91）：frequency 有值时只从词频 top-200 抽。当前种子数据 frequency 全为 0 → 走全表洗牌（CET4 4686 词），现状安全；但若将来灌入词频数据会静默退化为 top-200 池。实施时在代码注释中记录此陷阱。
- **`MIN_WORDS_PER_CONTENT=5` 被 word_card/quiz 共用**（word-card.service.ts:14、quiz.service.ts:15），不能直接改值 → 新增 scene_word 专用常量。

## 新流程（V4）

```
词表组装（循环外一次）
  1. fetchTopicWords(topic, level) → LLM 列 ≤15 主题词 → validateWords 查库过滤 → topicPool
  2. randomWords(level, 120 - topicPool.length) → randomFill（当前=全表随机）
  3. wordList = topicPool ∪ randomFill（去重；来源标注 topic / random，narrative 来源废除）

重试循环（最多 3 次，每次全新对话）
  4. 目标词数 T = input.wordCount ?? (8 + floor(random*9))   // 未显式指定则随机 [8,16]
  5. buildPrompt：中文故事 + 自然使用词表中文含义 + 每段 words 数组标注用到的英文词
  6. LLM 输出 {topic, title, segments:[{text, words: string[]}]}
  7. resolveSegmentWords（每段）：
       候选 = 该段 words 标注 ∪ extractEnglishWords(text)   // 标注为主，漏标从文本提取兜底
       → validateWords 查库 → 不在词库的剔除
  8. 定向注入（每段）：复用现有 injectFromDict，把命中词的中文义项替换为英文词
       → text 变为中英混杂，渲染器 \b 高亮可用
  9. acceptOutput：topicMatch && 全篇唯一英文词数 ≥ 8；不通过携带原因反馈重试

成功 → 组装 ContentDTO（words 全篇去重，超 20 按首次出现顺序截断）
3 次失败 → throw Error(`内容生成未通过验收：${lastFeedback}`)
```

与旧流程的本质差异：

| | 旧（V3） | 新（V4） |
|---|---------|---------|
| 固定死列表 | NARRATIVE_WORDS 必进池 | 删除 |
| 词表大小 | ~20 | 120（主题词优先 + 大随机池） |
| 英文词入文方式 | 扫描全部候选词释义盲替 | 只注入 LLM 标注（+文本提取兜底）过的词 |
| 词数下限 | 5 | 8（scene_word 专用常量） |
| 词数目标 | 固定 | 每次随机 T∈[8,16]（用户要求"8~20 随机"） |

## 详细设计

### 1. 词表组装 `buildWordList`（替代 buildCandidates）

```ts
const WORD_LIST_SIZE = 120;

async function buildWordList(input: GenerateSceneWordInput): Promise<{
  words: { word: string; meaning: string; level: "CET4" | "CET6" }[];
  sources: CandidateSource[];
}> {
  // 主题词：LLM 产出 → 词库把关（保留，保证故事贴合主题；失败返回 [] 不阻塞）
  const topicWords = await fetchTopicWords(input.topic, input.level);
  const { matchedWords: topic } =
    topicWords.length > 0 ? await validateWords(topicWords, input.level, db) : { matchedWords: [] };

  // 随机补足（当前数据 frequency=0 → 全表随机；未来若启用词频需复查 top-200 退化问题）
  const { words: randoms } = await randomWords(input.level, WORD_LIST_SIZE - topic.length, db);

  // 合并去重，主题词排最前（prompt 中优先展示）
  const seen = new Set<string>();
  const words = [...topic, ...randoms].filter((w) => {
    const k = w.word.toLowerCase();
    if (seen.has(k)) return false;
    seen.add(k);
    return true;
  });
  return {
    words,
    sources: [
      ...topic.map((w) => ({ source: "topic" as const, word: w.word })),
      ...randoms.map((w) => ({ source: "random" as const, word: w.word })).filter(
        (s) => !topic.some((t) => t.word.toLowerCase() === s.word.toLowerCase()),
      ),
    ],
  };
}
```

- `CandidateSource["source"]` 收窄为 `"topic" | "random"`（删除 `"narrative"`）。历史 audit JSON 中已存的 narrative 值仅作展示，无解析逻辑，不受影响。
- 重试循环**不重建词表**（主题词只需取一次；词表固定可让 LLM 在重试时修正而非换题）。

### 2. Prompt（buildPrompt 改造）

```text
你是英语学习内容创作者。为 CET{4|6} 级别制作情景背词短视频。

【主题】{topic}

【要求】
1. 写一个中文情景故事，情节连贯、生活化，标题也用中文（不超过 20 字）
2. 故事必须紧紧围绕主题「{topic}」展开
3. 从下方词表中挑选约 {T} 个单词（范围 8~20），把它们中文含义自然写进故事
   （如词表有「contract 合同」，故事里就出现「合同」这类字面一致的词）；务必自然，不要罗列
4. 对每段用到的词表单词，在该段 segments 的 words 数组里列出对应英文单词
5. 正文分 {segments} 段（每段 60-120 字），topic 字段回显你理解的主题
6. 只输出一个 JSON 对象，不要任何其他文字、不要 markdown 围栏

【词表】（用到的词必须来自此表，每行：word（义项））
{wordList}

【输出格式】（示例内容不可复用）
{"topic":"科技创业","title":"一次科技创业","segments":[
  {"text":"Leo签下一份合同，计划扩张业务。","words":["contract","expand"]}]}

【上次错误，必须修正】        ← 仅重试时追加
{lastFeedback}
```

- **wordList 渲染注意**：prompt 中每个词的义项只取前 2 个（`splitMeanings(meaning).slice(0,2).join("；")`），控制 prompt 体积（120 词 × 全量释义会显著变长）；注入阶段仍用全量义项。
- 关键措辞是"字面一致"：LLM 写的故事里必须出现词表义项的原词（如"合同"），否则第 7/8 步匹配不到会被剔除或注入失败。

### 3. LLM 输出 Schema 变更

```ts
// llmOutputSchema：words 从对象数组改为字符串数组（模型只标单词，词义以词库为准）
const llmOutputSchema = z.object({
  topic: z.string().min(1),
  title: z.string().min(1).max(60),
  segments: z.array(z.object({
    text: z.string().min(1),
    words: z.array(z.string().min(1)).optional(),   // optional：漏标由提取兜底
  })).min(1),
});
```

最终 ContentDTO 的 `SceneWordSegment.words` 结构不变（仍是 `{word, meaning, level}[]`，来自词库查询结果），**shared 包类型与 API 契约零改动**。

### 4. 每段词解析 `resolveSegmentWords`（新增，替代 injectSegments 的校验部分）

```ts
async function resolveSegmentWords(
  seg: { text: string; words?: string[] },
  level: "CET4" | "CET6",
): Promise<DictFilteredSegment> {
  const text = seg.text ?? "";
  const candidates = [...new Set([...(seg.words ?? []), ...extractEnglishWords(text)])];
  const { matchedWords } = await validateWords(candidates, level, db);
  return {
    text,
    words: matchedWords.map(({ word, meaning, level: lv }) => ({ word, meaning, level: lv })),
  };
}
```

两层保障：
1. LLM 标注的词 → 必须在词库（不在的剔除）
2. 从 text 提取英文词（模型自写英文 / 漏标兜底）→ 词库命中后并入

### 5. 定向注入（复用 injectFromDict）

```ts
const resolved = await Promise.all(
  llmOutput.data.segments.map((seg) => resolveSegmentWords(seg, input.level)),
);
const injected = resolved
  .filter((seg) => seg.text.trim().length > 0)
  .map((seg) => injectFromDict(seg.text, seg.words));
```

- **injectFromDict 不删除**（旧文档要求删除是错的）：它承担"中文义项 → 英文词"的文本替换，是高亮体验的基础。变化在于候选范围从"全池盲扫"收窄为"LLM 标注 + 文本提取确认过的词"，消除误注入。
- 注入后某段可能一个词都没换上（LLM 标注的词与文中措辞不一致）→ 由第 9 步验收兜底重试。

### 6. 词数验收与截断

```ts
/** scene_word 专用下限：用户期望每篇 8~20 词；word_card/quiz 仍用 MIN_WORDS_PER_CONTENT=5 */
export const SCENE_MIN_WORDS_PER_CONTENT = 8;
```

- `acceptOutput`：`total < SCENE_MIN_WORDS_PER_CONTENT` 时拒绝，反馈见下表。
- 超过 `MAX_WORDS_PER_CONTENT=20`：按单词在文本中首次出现顺序保留前 20 个（沿用《问题1-详细方案》§四的截断代码思路，在组装 DTO 前执行）。
- 目标值 T：`input.wordCount` 显式传入时 clamp 到 [8,20] 使用；否则每次随机 `[8,16]`——落实用户"8~20 之间随机"的要求，也让连续生成的篇目自然差异化。

### 7. 重试机制（≤3 次，每次全新对话）

| # | 条件 | 反馈给 LLM |
|---|------|-----------|
| 1 | JSON 解析失败 | 输出不是合法 JSON（必须只输出一个 JSON 对象，不要任何其他文字或 markdown 围栏） |
| 2 | topic 偏离 | 主题偏离：要求围绕「X」，你输出的主题是「Y」。请重新围绕「X」编写故事 |
| 3 | 有效词 < 8 | 有效词仅 {N} 个（要求至少 8 个）。请确保：① 用到的词来自词表并在 words 数组中标注对应英文单词；② 故事里写出这些词的中文含义且与词表义项字面一致（如词表写「合同」，故事就写「合同」） |

- 反馈文案必须引导 LLM"字面写出义项"，这是注入命中的前提。
- 3 次仍失败：`throw new Error("内容生成未通过验收：" + lastFeedback)`（现状行为不变，500 响应体展示原因）。

### 8. 兜底机制总表

| 兜底 | 位置 |
|------|------|
| JSON 解析失败 | extractJson + llmOutputSchema.safeParse → 重试 |
| LLM 没写 words 字段 | resolveSegmentWords 从 text 提取英文词兜底 |
| LLM 用了词表外的词 / 编造词义 | validateWords 查库剔除 |
| 标注了但文中找不到义项（注入落空） | 验收统计以注入结果为准 → 不足 8 个拒绝重试 |
| 词数太多 | MAX_WORDS_PER_CONTENT=20 按出现顺序截断 |
| 主题词调用失败 | fetchTopicWords 内部 catch 返回 []，纯随机池顶上 |
| 3 次都失败 | throw Error，前端展示具体原因 |

# 问题 2：上传标记弹窗第一次点击显示旧标记

## 根因

`upload-mark-manager.vue` 的 `marks` ref 在弹窗关闭后保留旧文件的数据；下次打开时 `load()` 异步请求期间模板渲染的仍是旧值。同理 `editingId` 也可能残留（上个文件的编辑态）。

## 改动文件

`packages/frontend/src/components/upload-mark-manager.vue`

## 改动内容

打开弹窗时清空全部瞬时状态（不止 marks）：

```ts
function onOpenChange(v: boolean): void {
  open.value = v;
  if (v) {
    marks.value = [];           // 清空旧标记列表，避免闪现
    editingId.value = null;     // 退出可能残留的编辑态
    pendingDeleteId.value = ""; // 清理删除确认残留
    void load();
  }
}
```

可选增强（本次不做）：`watch(() => props.filename)` 在弹窗开着时切换文件则重新 load——当前所有调用方都是"先改 filename 再 open()"，打开时清理已覆盖。

# 问题 3：清理未引用只删视频不删音频

## 根因

`Files.vue` 的 `openCleanup/doCleanup` 过滤条件写死 `f.type === "video"`，且 `batchDeleteFiles` 的 type 硬编码 `"video" as const`。

后端 `file-manager.ts` 的 `FILE_TYPES = ["audio","video","bgm"]` 已支持三种类型批量删除，无需后端改动。

## 决策 D3：全局清理

范围用 `files.value`（全部文件）而非 `filtered.value`（当前 Tab），避免"在视频/BGM Tab 下点清理却清不到音频/清不到东西"的困惑。

## 改动内容

```ts
/** 未引用 = 无任何生成记录引用；BGM 是素材永不清理 */
const collectOrphans = (): { filename: string; type: "audio" | "video" | "bgm"; referencedBy: { id: string; title: string }[] }[] =>
  files.value.filter((f) => f.type !== "bgm" && f.referencedBy.length === 0);

function openCleanup(): void {
  const orphans = collectOrphans();
  if (orphans.length === 0) {
    toast.success("没有可清理的未引用文件");
    return;
  }
  const videos = orphans.filter((f) => f.type === "video").length;
  const audios = orphans.length - videos;
  cleanupTip.value = `将删除 ${orphans.length} 个未被任何生成记录引用的文件（视频 ${videos} 个、配音 ${audios} 个，含其上传标记），不可恢复。BGM 素材不受影响。`;
  cleanupOpen.value = true;
}

async function doCleanup(): Promise<void> {
  const orphans = collectOrphans();
  try {
    // type 必须逐项透传真实类型（旧代码硬编码 "video"）
    const result = await batchDeleteFiles(
      orphans.map((f) => ({ filename: f.filename, type: f.type })),
    );
    await load();
    await loadMarks();
    if (result.errors.length > 0) {
      toast.error(`已清理 ${result.deleted} 个；${result.errors.length} 个失败（${result.errors.map((e) => e.filename).join("、")}）`);
    } else {
      toast.success(`已清理 ${result.deleted} 个未引用文件`);
    }
  } catch (err) {
    errorMsg.value = err instanceof Error ? err.message : String(err);
  } finally {
    cleanupOpen.value = false;
  }
}
```

配套文案同步（易漏项）：
- 按钮 `title` 属性："删除未被任何生成记录引用的视频文件" → "删除未被任何生成记录引用的视频和配音文件"
- ConfirmDialog `title`："清理未引用视频" → "清理未引用文件"
- `errors` 分支处理与 `doBatchRemove` 保持一致（原方案遗漏）

# 问题 4：视频/文案中带"修改"类文字（暂缓，待诊断后对症处理）

## 核实结论（2026-08-23 源码复核）

"修改日志"机制**不可能**把文字带进视频/文案：
- `modifications` 仅写入 `contents.audit` JSON 列（tasks.ts:288-298），与渲染用的 `content` 字段分离
- 渲染器与 TTS 只读 `content`/`title`，从不读 audit；`reconcileWords`（tasks.ts:82）只同步词汇标签、不改正文

## 真实来源假设（按可能性排序）

| # | 假设 | 依据 |
|---|------|------|
| H1 | **TTS 全中文朗读的反替换**：buildTtsText（tts.service.ts:319-330）把正文英文词原位替换为中文释义配音；revise/modify/amend 的释义就是"修改"。每次编辑→重新配音→听到"…修改…"，画面高亮的却是 revise | 最可能；符合"每次修改时都会出现" |
| H2 | 前端档案面板误导：TaskDetail 底部"生成档案"面板的"修改日志：xxx"、AuditList 表头"修改次数"被当成文案一部分 | 次可能 |
| H3 | 历史脏数据：个别旧记录 content 被写坏 | 无法排除，需查库 |

## 处理流程（重启本问题时执行）

第一步诊断（约 10 分钟）：
```sql
-- 取一条问题记录，确认 content 正文是否含"修改"二字（排除/确认 H3）
SELECT id, title FROM contents
WHERE JSON_SEARCH(content->>'$[*].text', 'one', '%修改%') IS NOT NULL;
```
再播放该记录音频，对照画面高亮词，确认"修改"是否为某高亮词的中文释义（H1）。

第二步按结果对症：

| 定位结果 | 处理 | 成本 |
|----------|------|------|
| H1 反替换念释义 | 设计行为（2026-08-17 用户确认全中文朗读）；若介意可选：高亮词保留英文不替换 / 念完释义补读原词 | 小 |
| H2 UI 误导 | 档案面板加说明"仅操作记录，不影响成片"；或修改日志只在审计页展示 | 极小 |
| H3 脏数据 | 清洗数据，无代码改动 | 小 |
| 用户不需要审计功能 | 删 PATCH modifications 入库 + 前端隐藏区块（PRD 10.1.4 要求此 MVP，放弃需用户拍板） | 小 |

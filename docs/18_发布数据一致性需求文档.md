## 一、问题陈述

用户按「一天一集」生产内容，到 2026-10-02 累计 **44 集**。但后台五个页面给出五个不同的数：

| 页面 | 显示条数 | 实际数据源 | 差额的可解释原因 |
|------|---------|-----------|----------------|
| 文件管理 | 44（其中 2 个未引用） | 磁盘 `uploads/video/*.mp4` | 42 个被 `contents` 引用 + **2 个孤儿成片** |
| 发布管理 `/analytics` | 43 | `contents` 表 | 42 个真实集 + **1 条测试夹具 `test0001scene`** |
| 视频资产 `/videos` | 43 | `contents`（`video IS NOT NULL`） | 同上（43 行全部有成片） |
| 审计管理 `/audit` | 43 | `contents` | 同上 |
| 上传标记 `/marks` | 42 | `upload_marks` | **正好等于 42 个真实集**（夹具无标记、零孤儿标记） |
| 数据分析 `/insights` | 39 | `publish_records` INNER JOIN `contents` | 38 个真实集 + 1 条夹具；**6 集静默不可见** |

结论：**这不是显示 bug，是「一集视频」在系统里没有唯一定义**。每个页面各自挑了一张表当分母，所以数字必然不一致；而真正的数据损失（第 39、40 集）恰好被这种口径混乱掩盖，用户只能靠肉眼发现「少了两集」。

### 1.1 第 39、40 集发生了什么（已取证）

`contents` 表的日期序列在 09-23 之后直接跳到 09-29，**09-24 与 09-25 两天的整行记录不存在**。但宿主机上留着两个同日期、未被任何记录引用的成片：

| 集数 | 成片文件 | 时长 | 截帧识读出的标题 | 同期孤儿配音 |
|------|---------|------|----------------|-------------|
| 第 39 集 | `93c90a30-7d53-4b10-8930-a8b5699b04b2.mp4`（09-24 19:12） | 29.91s | 《家庭聚餐欢乐夜》 | `cbfe843e-8bc4-45e6-916a-bde6317281c7.mp3`（09-24 19:10） |
| 第 40 集 | `ab682d56-2164-4872-9937-eab274ff5500.mp4`（09-25 19:31） | 35.63s | 《通勤中的地铁之旅》 | `6eeb2009-da6d-4082-ba16-911dff8de489.mp3`（09-25 19:31） |

两帧画面完整渲染出「标题 + 两段正文 + 本期词汇表」，因此这两集的**标题、正文文案、词表、配音、成片五样全部可取回**，只缺数据库那一行。

- 第 39 集词表（12）：invite 邀请 / friend 朋友 / relative 亲戚 / table 餐桌 / meal 膳食 / dinner 正餐 / family 家庭 / toast 烤面包 / enjoy 享受 / spoon 调羹 / fork 餐叉 / dessert 甜食
- 第 40 集词表（12）：timetable 时刻表 / need 需要 / crowd 聚集 / morning 早晨 / map 地图 / platform 平台 / subway 地铁 / train 列车 / traffic 交通 / evening 傍晚 / line 路线 / card 卡片

**归因**：2026-09-28 那次「测试库 16 张业务表 mysqldump 灌回生产库」以 09-23 时代快照替换了生产 `contents` 等表（PROGRESS 记录导入后 contents=41 = 38 真集 + 3 夹具）。09-24、09-25 两集创建于该快照之后，因此在替换中丢失；成片与配音写在宿主机目录，未受表替换影响而幸存。
**同时**：那次导入把测试夹具 `test0001scene` 及其两条 `testpub*` 发布记录带进了生产库——夹具还复用了第 20 集（数字断舍离）的成片文件名，是各页面数不一致的第二个来源。
**已否证的猜测**：生产 binlog 最早一份起于 09-28（新数据卷），不含 09-24/25 的行事件，因此 binlog 不是本次可用的恢复源；PROGRESS 所述取证盘 `data.img.corrupted-20260928.bak` 在本次审计中未在本机定位到，不作为恢复依赖。

## 二、用户故事

### US-1　生成后的标题就是我在发布管理看到的标题
**作为**内容生产者，**我希望**发布管理列表的标题列显示这一集生成出来的标题，除非我自己在发布面板里显式改过它，**以便**我不需要猜「未命名」是哪一集。

现状：`cnt_20261002_469bc3`（生成标题《线上学习的新支持》）在发布管理显示「未命名」，因为它的 `video_analytics.story_topic` 快照为 NULL，而读取端只要快照行存在就只认快照、前端又把 NULL 合并成空串，把本来来自生成标题的兜底也覆盖掉。

### US-2　我标了「已上传」就等于这一集发布了
**作为**内容生产者，**我希望**在上传标记里标一条视频已上传某平台时，系统自动把这一集纳入发布与分析口径，**而不是**我事后还要去「数据接入」页手工建发布记录。

现状：`POST /api/upload-marks` 只写 `upload_marks` 一张表，与 `publish_records` 完全脱钩。生产库 42 个真实集**全部有上传标记**，但只有 38 个有发布记录——09-29~10-02 四集因缺发布记录在数据分析整行不可见。这是「数据分析只有 39 条」的直接原因。

### US-3　任何一集都不该在任何页面静默消失
**作为**内容生产者，**我希望**某一集在某个视图里不出现时，界面明确告诉我它为什么不在（未标记发布 / 未登记作品 ID / 未渲染成片），**以便**我不用靠数数来发现丢数据。

### US-4　各页面的数对得上，对不上时能一眼看到差在哪
**作为**内容生产者，**我希望**「一共多少集」这件事在系统里只有一个口径；发布管理、视频资产、审计、标记、发布记录、成片文件之间的数量差异要么为零，要么在界面上被显式列出并给出处理入口。

### US-5　侧边栏可以收成只剩图标
**作为**在小屏上长时间使用的用户，**我希望**侧边栏旁边有一个按钮，点击在「完整侧边栏」和「只剩图标」之间切换，图标态下悬停浮出名称，并且刷新后记住我的选择。
（本条属独立功能，走单独分支与单独提交，不与数据一致性修复混在一条分支上。）

## 四、验收标准

### 4.1 代码行为（开发库 :3307 验证，全部门禁绿）

1. `video_analytics.story_topic` 为 NULL 或空串的内容，发布管理标题列显示 `contents.title`，**不再出现「未命名」**；用户在发布面板显式改过主题时，改后的值优先（生产现存 `cnt_20260919_8e02dc` 快照「选修课翻车」vs 生成标题「选修课的冲突」，须仍显示「选修课翻车」）。
2. 新建上传标记（平台=抖音，链接含 `douyin.com/video/<id>`）后，**不额外操作**即可在 `/api/analytics/publish-records` 查到对应发布记录，`platform_videoId` 为解析出的作品 ID；重复标记同一集同一平台不产生第二条记录；标记无链接时仍派生记录，`platform_video_id` 保持 NULL（不造假数据）。
3. 删除上传标记**不**级联删除已派生的发布记录（指标挂在发布记录上）；此语义须在界面上可理解。
4. 数据分析页顶部在存在未标记发布的集时显示「另有 N 集未标记发布」，N 与服务端口径一致。
5. 发布管理 / 生成记录在总数超过单页容量时不丢行，KPI 数字等于服务端 `total` 而非已加载条数。
6. `pnpm typecheck` 3/3 通过、`pnpm lint` 零告警、后端与前端单测全绿、`pnpm openapi:check` 8/8、`pnpm e2e`（真实测试栈）无新增失败。

### 4.2 数据修复（开发库演练终态对账表）

在开发库复刻生产数据形态后执行修复脚本，须达到：

| 指标 | 期望值 | 说明 |
|------|-------|------|
| 磁盘成片文件数 | 44 | 与生产一致 |
| `contents` 行数 | 44 | 42 现存真集 + 2 恢复集；测试夹具 0 |
| 未被引用的成片文件 | 0 | 第 39/40 集成片重新被引用 |
| 复用同一成片文件的多条记录 | 0 | 夹具与第 20 集共用的 `da40d3dc…mp4` 冲突消除 |
| `publish_records` 行数 | 42 | 每个有上传标记的真集一条，无重复绑定 |
| `upload_marks` 行数 | 42 | 零孤儿 |
| 数据分析可见集数 | 42 | 与发布记录同源 |
| 未标记发布的集 | 2 | 第 39/40 集，界面显式提示，不伪造标记 |

恢复出的两条 `contents` 行必须满足：`status='completed'`、`video`/`audio` 指向盘上真实存在且可播放的文件、`content`/`words` 与截帧识读的文案词表一致、`audit` 中标注恢复来源（不伪装成 LLM 原始生成档案）。

### 5.1 演练结论（2026-10-02，已在开发容器实测）

演练方式：生产库 `mysqldump --single-transaction`（只读）→ 灌入开发容器独立库 `recover_rehearsal`（18 表，43/40/42/5 与生产全等）→ 跑脚本 → 再用真实后端进程连该库打接口复核。

| 验收项 | 期望 | 实测 |
|--------|------|------|
| 脚本幂等（二次 `--apply`） | 零变更 | `[A] 无夹具跳过 / [B] 42 条 unchanged / [C] 已存在跳过` ✅ |
| 修复后对账 | 44/0/44/42/42/42/0/2/0 | 完全一致 ✅ |
| 恢复行 JSON 形态 | 与真实记录同构 | `{word, level, meaning}`、每段 7 词、无词性前缀 ✅ |
| `GET /api/video-analytics` | 未覆盖→`storyTopic: null`；已覆盖→保留 | 第 44 集 `null`；`cnt_20260919` 仍为「选修课翻车」✅ |
| `GET /api/analytics/videos` | 42 条 + 未登记 2 | `total:42, unregisteredContentCount:2` ✅ |
| `POST /api/upload-marks` | 自动派生发布记录 | `publishRecord:"created"`，作品 ID 解析成功、`publishTitle` 为恢复集标题 ✅ |

| 标记后联动 | 分析页 total+1、未登记−1 | 42→43、2→1 ✅ |

### 5.2 生产执行步骤

```bash
# ① 只读审计：确认生产仍是演练时的形态（任一数字对不上就先停下，不要直接跑脚本）
docker exec language-flow-mysql mysql -udev -pdev --default-character-set=utf8mb4 language_flow -t -e "
SELECT (SELECT COUNT(*) FROM contents) contents_rows,
       (SELECT COUNT(*) FROM contents WHERE id LIKE 'test%') fixture_rows,
       (SELECT COUNT(*) FROM publish_records) publish_rows,
       (SELECT COUNT(DISTINCT content_id) FROM publish_records) published_contents,
       (SELECT COUNT(*) FROM upload_marks) mark_rows;"

# ② 备份（回滚唯一依据，必须先做）
mkdir -p ~/language-flow-backup-$(date +%Y%m%d)
docker exec language-flow-mysql mysqldump -udev -pdev --single-transaction language_flow \
  > ~/language-flow-backup-$(date +%Y%m%d)/prod-before-recover.sql

# ③ 演练（可选但推荐）：临时库跑一遍
#    脚本默认 dry-run，只打印将要做什么，不写一行

# ④ 生产执行：护栏要求显式放行（AGENTS.md §零：不得为图便利写生产库）
cd packages/backend
DATABASE_URL='mysql://<user>:<pass>@127.0.0.1:3306/language_flow' \
DB_ALLOW_PROD=1 UPLOADS_DIR="$HOME/language-flow-uploads" \
  npx tsx scripts/recover-publish-data.ts          # 先看 dry-run 输出
DATABASE_URL='mysql://<user>:<pass>@127.0.0.1:3306/language_flow' \
DB_ALLOW_PROD=1 UPLOADS_DIR="$HOME/language-flow-uploads" \
  npx tsx scripts/recover-publish-data.ts --apply  # 确认无误后执行

# ⑤ 回滚（仅在结果不符预期时）
docker exec -i language-flow-mysql mysql -udev -pdev language_flow \
  < ~/language-flow-backup-$(date +%Y%m%d)/prod-before-recover.sql
```

### 5.3 脚本的三条安全性质

- **默认 dry-run**：不带 `--apply` 不写库；dry-run 阶段的回填判定走只读预览，不会调用写入路径。
- **生产库护栏**：目标是回环 `:3306` 时 `requireSafeWriteTarget()` 直接中止，必须显式 `DB_ALLOW_PROD=1`（复用仓库既有 db-guard，不新造一套）。
- **媒体文件前置校验**：恢复两集前逐个 `stat` 音/视频文件，缺失即拒绝插入该行——不制造「记录存在但文件不存在」的新裂缝。

### 5.4 明确不在脚本里做的事

- 不给恢复的两集造 `upload_marks`（无发布证据）；它们会留在 `unregistered_episodes=2` 里，由分析页提示条显式呈现。
- 不还原两集的 `audit` 生成档案（候选词/重试历史不存在），只写 `audit.recovered` 痕迹。
- 不动 `video_analytics` 快照（`cnt_20260919` 的「选修课翻车」是用户显式改过的覆盖值，保留）。
- 不删磁盘上的任何文件；孤儿成片在恢复后自动变为「已引用」。

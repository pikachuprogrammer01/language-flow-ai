# 17 · 视频数据分析模块设计（Content Learning Engine）

> 状态：Phase 1~4 + Phase 6（数据基础/看板/因子分析/优化闭环/内容实验）已实现 · 2026-09-24 · Phase 5 模型按数据量门槛待启动 · 2026-09-26 审查修正批次 1/2A/3/4 落地（§十一「审查修正记录」）
> 需求源：《视频数据分析 + 内容效果归因 + 下一条视频优化》模块需求（全 29 节，下称"需求"）
> 关联：SPEC §5.6（API 契约）/ §10.5~10.9（表结构）/ docs/16（API 规范）/ docs/15（生成服务）
> 定位：平台内置模块，非独立 BI 系统；所有分析必须能回流 选题→生成→配音→渲染→发布 生产流程（需求 §四）。

---

## 一、模块使命与闭环

```
Create → Publish → Analyze → Optimize → Create
```

回答四个问题（需求 §三/§二十一）：

1. 为什么用户没有停下来？（首帧/0-2s/0-5s/Hook → 2 秒跳出率、5 秒观看）
2. 为什么用户没有看完？（时长/节奏/知识点/CTA → 平均观看时长、完播率）
3. 为什么看完却没关注？（系列感/CTA/主页访问 → 播放→主页→关注漏斗）
4. **下一条视频应该怎么做？**（最终输出：推荐回流到 Create 页参数预填）

## 二、三层数据体系（需求 §五）

| 层 | 定义 | 实现 |
|----|------|------|
| A. Production Data | 平台生产阶段事实（最重要数据资产） | `content_features` 从 ContentDTO/audit/渲染产物直取，**禁止对已知事实做 AI 二次猜测** |
| B. Performance Data | 发布后外部结果 | `video_metrics` / `video_metric_daily`（累计+每日快照）、`creator_metric_daily`（账号日聚合）；来源 = Creator Import（唯一外部入口，抖音通道已砍除）/ 手动录入 |
| C. Derived Data | 平台计算指标 | `PLATFORM_CALCULATED` 落库，后端统一计算（需求 §二十四），除零/缺输入 → 不落值（无数据 ≠ 0，需求 §二十六） |

### 派生指标口径

```
2秒有效播放率 = 1 - 2秒跳出率
点赞率/评论率/分享率/收藏率/主页访问率 = 对应计数 / 播放量
互动率 = (点赞+评论+分享) / 播放量
平均观看比例 = 平均播放时长 / 视频时长（production 事实）
```

**归因诚实性**：账号日新增粉丝（`creator_metric_daily.new_fans`）**不得**宣称为某单视频带来；视频级 `new_fan_count` 仅可导入且自动标记 `is_estimated=1`（相关性分析/时间窗口归因/估算值）。

## 三、每个指标必须可溯源（需求 §六）

`video_metrics` 行携完整 provenance：`metric_name / metric_value / source_type / source_field / data_date / fetched_at / is_estimated / confidence / metadata`。

`source_type` 五值全集（抖音通道砍除后收敛，2026-09-24 用户决策）：`CREATOR_IMPORT · PLATFORM_PRODUCTION · PLATFORM_CALCULATED · AI_EXTRACTED · USER_INPUT`，不保留 DOUYIN_* 死值。

前端展示指标时**必须**带来源标签（如「完播率 41.3% [创作者导入]」），绝不让用户误认为全部来自抖音官方。

## 四、统一 ID 链路（需求 §七）

```
content_id（contents.id，生产唯一）
   ↓
publish_record（platform + platform_video_id 唯一 —— 抖音 item_id）
   ↓
video_metrics / video_metric_daily
```

- `video_asset_id` = uploads/video 文件名（创建发布记录时自 `contents.video.url` 派生）。
- **禁止标题模糊匹配**维护生产视频↔平台作品关系（导入匹配仅 recordId / platformVideoId / platform+contentId）。
- 原需求链路中 `project_id / script_id / script_version / prompt_version`：平台当前无独立项目/脚本实体，`content_id` 即生产根 ID；`prompt_version`/`renderer_version` 在 audit 未留痕前保持 null（不猜测，不建空实体）。

## 五、canonical 指标目录与可用性分级（需求 §二十二）

单一事实源：`packages/backend/src/lib/analytics-taxonomy.ts`；API `GET /api/analytics/metric-catalog` 暴露给前端动态渲染（字段不写死）。

| canonical 名 | 中文 | availability | 说明 |
|---|---|---|---|
| play_count / like_count / comment_count / share_count | 播放/点赞/评论/分享 | IMPORT_ONLY | 无官方 API 可达通道，仅导入可达 |
| collect_count | 收藏 | IMPORT_ONLY | 无 OpenAPI 字段 |
| bounce_rate_2s / watch_rate_5s / avg_watch_time / completion_rate | 2s跳出/5s观看/平均时长/完播 | IMPORT_ONLY | 仅创作者后台可得 |
| profile_visit_count | 主页访问 | IMPORT_ONLY | — |
| new_fan_count（视频级） | 视频新增粉丝 | IMPORT_ONLY | 导入自动标 is_estimated |
| effective_play_rate_2s / like_rate / comment_rate / share_rate / collect_rate / engagement_rate / avg_watch_ratio / profile_visit_rate | 比率族 | DERIVED | 平台计算，不接受导入 |
| traffic_source_distribution | 流量来源结构 | FUTURE | Phase 3+ 承接 |

（未列字段一律视为 FUTURE；接入任何外部字段前先核实真实存在，禁止假设。）

## 六、内容标签体系（需求 §十，scene_word 优先）

taxonomy 常量在 `analytics-taxonomy.ts`（zod enum 同源校验），**可扩展不锁死**：

- Scene：restaurant/airport/hotel/workplace/interview/shopping/hospital/school/travel/dating/social/daily_life
- Hook：mistake/warning/question/conflict/curiosity/quiz/pain_point/counter_intuitive/identity/result_first
- Content Format：scenario_dialogue/scenario_teaching/pure_teaching/mistake_correction/quiz/shadowing/vocabulary/story
- Emotion：funny/awkward/surprise/conflict/warm/tense/curious
- CTA：follow_series/follow_account/like_comment/next_teaser/collect_save/none

Phase 1 口径：这些标签生产阶段未建模 → `content_features` 对应列仅接受 `USER_INPUT`（PATCH 覆盖），重算保留；后续 AI 提取接入时记 `AI_EXTRACTED`。

## 七、数据源接入决策（原需求 §二十三 Adapter 的收敛）

用户决策（2026-09-24）：抖音开放平台需企业资质，本项目不具备 → **官方 API 同步通道整体砍除**：
- `AnalyticsDataProvider` 接口与 `douyinOpenApiProvider` 占位、`POST /api/analytics/sync` 端点删除；
- `availability` 的 CONDITIONAL 档删除，计数类指标改 IMPORT_ONLY；`source_type` 枚举收敛五值；
- 外部绩效数据唯一入口 = `POST /api/analytics/import`（推送式，动态映射）/ sourceType=USER_INPUT 同源录入；
- 前端唯一操作界面 = `/insights/data` 数据接入页（发布记录绑定 + 四步导入向导，逐视频/账号日双路径）。

### 账号日字段目录（CREATOR_DAILY_FIELDS，12 字段）

creator_metric_daily 列级白名单（与视频级 canonical 分开：口径不同不互串）：播放/点赞/评论/分享/主页访问/新增粉丝/粉丝总数 + 2秒跳出率/5秒完播率/平均播放时长/投稿量/封面点击率（后 5 项 2026-09-24 扩展）。`GET /metric-catalog` 同步暴露 `creatorDailyFields` 供前端动态渲染。可归属到视频的字段 = 前 9 项映射 canonical 指标；postCount/coverClickRate/totalFans 账号级专属。

## 八、Empty State 设计纪律（需求 §二十六）

- 刚发布无数据 → 显示「暂无数据 + 原因」，**不得显示 0%**：API 以 `emptyReason ∈ not_published | not_imported | null` 与指标缺失（而非 0 值）表达。
- 原因文案：尚未导入 / 平台不提供（availability=FUTURE）/ 创作者尚未导入 / 样本不足。
- 禁止「神秘爆款评分」黑盒综合分（需求 §十二）：任何评分必须先给出数据来源/模型/样本/指标意义；Phase 3 因子分析必须同时展示**样本数**。

### 数据边界演进（批次 5D：workspace/account 预留设计——只定边界，不提前改表）

当前数据模型隐含「单创作者、每平台单账号」假设，且刻进结构：`creator_metric_daily` 主键 `(platform, stat_date)`（无账号列）、`publish_records`/`content_features` 无归属列、全部分析查询无租户过滤。这是 MVP 的有意选择，不是遗漏；将来任一触发条件成立时按以下边界演进，**不在需求出现前预建空实体**：

- **触发条件**（任一）：① 需要第二平台账号/第二创作者导入（与批次 2B 产品形态裁决联动）；② 分析数据出现跨归属隔离需求（如代运营多号）。
- **演进路径**（届时另立批次评审）：新增 `workspaces` + `accounts`（platform + 账号标识唯一）两张实体；`publish_records`/`creator_metric_daily` 及导入端点增加 `accountId` 维度（`creator_metric_daily` 主键演进为 `(account_id, stat_date)`，纯增量迁移 + 存量回填默认账号）；全部分析查询参数化到账号集；路由层归属校验随认证方案（2B）一并引入。导入向导/指标目录/漏斗口径层均不受影响（数据按账号切片后同一套聚合逻辑）。
- **当下不变的约束**：单账号形态下任何代码不得预先塞入 accountId 参数（避免投机抽象）；新查询一律经 service 层收口，保证届时参数化只改 service 一处。

## 十二、四步精准匹配数据导入（2026-09-28 上线，替代旧逐行下拉框向导）

**目标**：将抖音/快手/视频号等平台导出数据导入系统，与视频作品（publish_records）建立尽可能准确的一一对应。核心原则：**系统自动完成确定性匹配，用户只处理异常**——唯一匹配批量确认，人工只碰冲突与未匹配；若实现退化为逐条人工选择即视为失败。

**四步流程（页面固定 Stepper，禁止删减/合并/换序）**：
1. **导入数据**：CSV/XLSX 浏览器解析（SheetJS，≤5000 行/批）→ 服务端字段识别（12 角色）+ **数据粒度三态判定**：`work_level_strong`（作品 ID/URL 非空占比 ≥90%）/ `work_level_weak`（有作品维度无强标识）/ `account_day_level`（仅日期+账号+指标）。判定依据（evidence.note + 占比）UI 原样展示；账号日级批次明确警示「无法精确归属到单条作品」，只能保存为账号日级数据；手动调整只允许降级。
2. **匹配规则**：账号映射/平台映射/时区/发布时间容差（默认 ±5 分钟）/标题标准化 5 开关/相似度阈值（默认 90%）；保存即 dry-run 四类预估（总/强匹配/人工确认/未匹配）；主操作「开始预匹配」点击才真正执行。
3. **匹配校验**：统计卡（全部/唯一匹配/待确认/未匹配/账号日级）点击即筛选 + 批量操作（一键确认全部唯一匹配/批量忽略/批量存账号级/重新匹配）+ 高密度表（导入侧+匹配侧+状态+依据）+ 右侧详情面板（导入记录/候选视频/证据 checklist/搜索绑定）。行状态六枚举 `unique_match/conflict/unmatched/account_day_level/confirmed/ignored`，禁增。
4. **提交落库**：十项 Preflight（③重复导入 file_hash/④未处理 CONFLICT/⑨非法数值/⑩重复提交阻断，其余 warning）通过才启用「确认导入」；提交服务端重验不信任前端态；四类计数展示（作品级/账号级/忽略/待处理冲突）。

**匹配引擎（`lib/import-matcher.ts` 纯函数，零 LLM）**：优先级固定 1 作品 ID 精确 > 2 URL 解析 ID（抖音 `/video/(\d+)`、快手 `short-video|photo`、视频号 `url=|/sph/`）> 3 账号+发布时间容差 > 4 账号+日+标准化标题相似（1-编辑距离/maxLen，标准化后去空白）> 5 +时长辅助（≤5s 升级）。强证据（1/2）单候选才 `unique_match`；弱证据单候选一律 `conflict`（用户裁决 2026-09-28）；多候选全部并列禁自动选最高分；强证据与弱证据不同指向并列展示矛盾。未绑定作品 ID 的记录不进引擎候选池（仅人工搜索绑定，防污染教训沿用）。每候选必存结构化 evidence（`platformWorkIdExact/accountMapped/publishTimeDiffSeconds/titleSimilarity/workIdMissing…`），前端逐条翻译成人话，禁裸置信度。

**数据模型（中间层四表 migration 0008，SPEC §10.14~10.17）**：`import_batch`（状态机 draft→granularity_confirmed→rules_set→prematched→preflight_ok→committed→rolled_back + file_hash 去重 + commit_preimage）→ `import_row`（raw_data 永久保留）→ `match_candidate`（一行多候选+evidence）→ `match_decision`（一行一决定+decision_type 追溯）。提交只写 `video_metrics`（作品级，复用 coerce/映射/派生重算单一口径，metadata.batch_id 溯源）与 `creator_metric_daily`（账号级），**禁止直写 video_analytics、禁止拆数/平均/推测**。回滚按 preimage 精确恢复受影响记录（含派生行与每日快照），已提交批次不可删除只可回滚（审计保留）。

**红线清单（代码级硬约束）**：账号日级行 UI 无归属按钮 + API assign 400；confirm 只接受 unique_match 行；external 行不落任何作品指标；raw_data 永不覆盖；批次可回滚。

**前端**：`/insights/import`（InsightsImport 壳 + import/ 组件族 + `lib/import-batch.ts` 纯函数）；`/insights/data` 保留发布记录绑定与新工作台入口卡；旧 `analytics-import-wizard.vue` 已删除（其后端 `POST /import`、`POST /creator-daily/import` 端点保留，已发布契约不破坏）。E2E：`e2e/import.spec.ts` 双用例（作品级全链路含回滚、账号日级红线含 API 400 断言）。

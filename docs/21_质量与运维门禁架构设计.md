## ① 技术方案

### 模块划分

三个彼此独立、可分别交付与回滚的能力，共用 `scripts/stack.sh` 既有助手（`log()` / `prod()` / `prod_env_get` / `ensure_mysql`）：

```
scripts/stack.sh
├─ cmd_backup        新增：生产库逻辑备份 + 成片增量快照 + 校验和 + 保留策略
├─ cmd_backup_verify 新增：把最新备份灌进临时 schema，按业务键与生产比对，用完清理
├─ cmd_audit         新增：生产库只读对账（纯 SELECT + 文件系统存在性核对），输出漂移清单
└─ cmd_release       改造：备份 → 质量门禁 → 才允许构建/改 APP_VERSION/up -d → 发布后健康复核
packages/backend/src/db/invariants.test.ts   新增：真库不变量测试（测试库，事务回滚）
```

pnpm 入口新增 `docker:backup`、`docker:backup:verify`、`docker:audit`；`docker:release` 语义不变但内部变严。

### 关键决策与取舍

**决策 1：备份必须同时覆盖数据库与成片目录。**
本系统的真实资产是"内容 JSON + 成片文件"两半。`publish_records.video_asset_id` 与 `contents.video` 存的是文件名，文件本身在宿主机 `~/language-flow-uploads`。只 dump 库，成片丢失时 `docs/18` 那次恢复就只能靠截帧反推文案。成片当前仅 69MB / 44 个文件，进备份包的成本是一次 tar/rsync，收益是把"不可恢复"变成"可恢复"。

**决策 2：逻辑备份用 `mysqldump --single-transaction`，不用卷快照。**
- 一致性：InnoDB `--single-transaction` 在不锁库的前提下拿到一致性快照，生产容器无需停机（正在跑的门禁/发布动作不受影响）。
- 可移植：dump 是纯 SQL，能恢复到任意 MySQL（测试实例即可验证），卷快照只能在同镜像版本上回放。
- 体量：5976 行词库 + 44 条内容，dump 只有几 MB，全量保留 10 份不心疼。
- 放弃 xtrabackup：为单机几千行的库引入外部工具链，维护成本远大于收益。
- 必须带 `--no-tablespaces`：`dev` 用户无 `PROCESS` 权限，缺这个参数会报 Access denied 且**退出码非 0**（`docs/18` 实测结论）。命令里显式判定 `$?`，不看字节数下结论。

**决策 3：成片用 `rsync -a --link-dest` 增量快照，不用全量 tar。**
每次产出一个完整可浏览的快照目录，未变更文件与上一份硬链接共享 —— 10 份保留的实际磁盘占用约等于 1 份 + 变更量。全量 tar.gz 10 份会稳定吃掉 700MB，且恢复时要逐个解包。代价：快照依赖文件系统支持硬链接（本机 APFS 满足）；跨机器复制备份包时会断开硬链接，因此备份目录**不设计为可搬到别处**（异地备份属范围外）。

**决策 4：备份"演一次真恢复"才算成功，比对只用业务键。**
恢复目标：测试实例上的临时 schema `lf_backup_check`，用 `root` 建库并授权给 `dev`，灌 dump，然后逐表比对。

| 表 | 比对键 | 为什么不能用自增 id |
|---|---|---|
| `contents` | `id`（业务侧生成的 varchar32） | — |
| `publish_records` | `(platform, platform_video_id)`，NULL 时退化用 `id` | 同上 |
| `video_metrics` | `(publish_record_id, metric_name)` | `id` 是 auto_increment，重灌夹具后整段漂移，按 id 比会报"全丢"的**假警报**（历史上真发生过） |
| `import_row` | `(batch_id, row_number)` | 同理 |
| `cet_words` | `(word, level)` | `id` 自增 |

演练结束必须 `DROP DATABASE lf_backup_check` 并回显已清理，不留残留物。

**决策 5：门禁放 `cmd_release`，不放 pre-push。**
风险发生在"切生产版本"那一刻，不在提交那一刻。pre-push 已经背着 typecheck + 全量单测（约 9s），再挂覆盖率与 E2E 会把日常提交拖成分钟级，反而诱发绕过。因此：日常快检维持现状，重活全部收口到发布前一次。

**决策 6：备份失败硬失败，质量步骤允许显式跳过。**
两者代价不对称——跳过备份省 20 秒，代价是丢掉唯一回滚路径且不可逆；跳过质量检查可以用 `docker:rollback <旧tag>` 挽回。所以 `GATE_SKIP=1` 只豁免"类型/单测/覆盖率/不变量/E2E 冒烟/生产对账"，不豁免备份；跳过时日志用醒目段落列出被跳过的步骤与生效方式（`deploy/prod.env` 未被静默改写）。工作树清洁检查同样不可跳过——那是镜像可复现性的前提。

**决策 7：不变量测试跑真库，且必须在事务里 seed→断言→回滚。**
backend 现有单测把 `db.transaction` 换成"直接回调"的替身，它验证的前提（原子性、级联、唯一键、FK）正是本项目出问题的地方。不变量测试用 `TEST_DATABASE_URL`（必须指向 :3307）建真连接，每个用例：开启事务 → 造夹具 → 断言 → `ROLLBACK`。好处是不污染 `docker/test-fixtures` 的夹具数据，测试栈可以反复复用；且没给 `TEST_DATABASE_URL` 时整个套件 skip——但 skip 会被发布门禁当红灯（见 DoD-4），不允许"静默不跑"变成通过。

钉住的不变量（≥9 条，逐条对应真实缺陷）：

1. **标记即发布**：插入 `upload_marks` 后同事务派生出 `publish_records`，且 `content_id`/`platform`/`video_asset_id` 与标记一致（回归"上传标记同事务派生发布记录"）。
2. **撤销标记不留孤儿**：删除该标记后不应残留发布记录（回归发布数据一致性）。
3. **级联清理真生效**：删 `contents` 行 → `publish_records`、`video_metrics`、`video_metric_daily`、`video_analytics`、`content_features`、`video_segments` 同步消失。
4. **FK 拒脏**：插入指向不存在 `content_id` 的发布记录，必须报错（MySQL 1452），不得静默落库。
5. **唯一键行为可预期**：`video_metrics (publish_record_id, metric_name)` 重复写入时报冲突而非静默覆盖——对账脚本的 upsert 依赖这个区分。
6. **`NULL platform_video_id` 不被唯一键去重**：同平台多条未回填作品 ID 可并存（钉住 `publish_records` 的已知陷阱，防止有人误以为唯一键能当对账去重依据）。
7. **`publish_at` >2038 往返**：`datetime` 存 2039 年取回一致（把 `integration.test.ts` 的 TX8 纳入常驻套件）。
8. **服务端 total 与 `count(*)` 对账，且 >100 行不丢**：事务内造 150 条，断言列表接口总数与逐行数一致（回归"100 条硬顶丢行"）。
9. **未登记发布记录的集数被透出**：有内容无发布记录的行必须出现在视频表现列表口径里（本分支新行为）。
10. **`contents.id` 事实不可变**：它被 6 张子表以 `ON DELETE CASCADE` 引用，但没有任何 `ON UPDATE CASCADE`，所以改主键必报 MySQL 1451（本轮做破坏演练时实测撞到）。钉住这条，防止将来有人以为可以"重编号"。

**决策 8：生产对账独立成命令，且只读。**
`cmd_audit` 只做 `SELECT` 与文件系统存在性检查：孤儿发布记录、标记与派生记录差额、`video_asset_id` 指向的成片是否存在、列表 total 与 `count(*)`，以及**集数序列断号**——`upload_marks.note` 里写着「情景英语四级词汇-第 N 集」，这个序列是产品负责人定位一集视频的主要入口，断号既是丢数据最直观的物理证据，也是他"看不看得见"的判断依据；只报 `contents` 行数对他是没有体感的。它被 `cmd_release` 在切换版本前调用一次——因为生产已经飘了而测试库全绿，是最坏的一种假绿灯。输出纪律：无漂移时明确"未发现漂移，未做任何修改"，不得报成失败；有漂移时按集数序列与逐表前后对账表呈现（含 `MAX(updated_at)` 作为"生产未变"的证据）；命令本体不持有写权限路径（不 `--apply`、无 UPDATE）。

**决策 9：覆盖率阈值改为实测水位，并只在发布门禁执行。**
backend 设 `statements 78 / branches 82 / functions 70 / lines 78`（实测 80.55/83.76/72.39/80.55，函数留最多吃掉空间）。frontend（99.66）与 shared（100）保持 90。执行点从"永远不跑的 `pnpm coverage`"改成发布链上的一步。配置文件注释必须写明这是**水位下沿而非目标**，否则下一次会有人把它当成待办去刷。

**决策 10：门禁必须打在新鲜产物上，且执行环境约束写进命令。**
本轮评估里翻过的一次跟头就是证据：一份"27 例中 9 失败"的 E2E 实测，随后按同一条命令复跑成 22 passed / 1 skipped——那次测量打在重建前的 `language-flow-test-*` 旧镜像上。同一个根因既能造出假红，也能造出**假绿**（旧镜像通过，新代码里的缺陷没被跑过）。因此门禁内部固定三条约束，不依赖执行者记得：

- 跑 E2E 前必须确认镜像构建时间晚于本次工作树 HEAD 的 commit 时间；不满足则由门禁自己触发 `pnpm docker:test` 重建，而不是拿旧镜像的结果放行。
- 重建后**先重灌夹具再跑 E2E**（`pnpm docker:test:seed`）：数据修复脚本会删 `test%` 行，次序反了用例必挂。
- 统一用 `E2E_BASE_URL=http://127.0.0.1:5174`（IPv4 字面量），避免 `localhost` 被无关项目的 vite 抢占 IPv6。

两条执行纪律同时入档：`pnpm -r test` 并行时 `file-manager` 的 reveal 用例会因 3 秒真实超时与前后端套件抢 CPU 偶发红——门禁遇到它重试一次并如实标注，**不得削弱断言换绿**；`cmd_release` 检查工作树时若存在**其他会话留下的未跟踪文件**，处置是临时移出、发布后原样放回并说明，禁止用 `FORCE=1` 绕过（`v8db33ce` 那个不可由 commit 复现的 tag 就是反面教材）。

## ③ 前端详细说明

**本轮无任何前端与 UI 变更**（不改 `packages/frontend/src/**`，不改样式与交互）。

CLI 侧的输出形态按"点了要知道成没成"设计：

- `docker:backup`：实时逐段输出（dump 中 → gzip → sha256 → 成片快照 → 保留策略命中/删除了哪几份 → 恢复演练中 → 比对表），结束时给出**最终结果块**：备份目录路径、各文件大小、恢复演练逐表比对结果、清理确认。
- `docker:release`：门禁按步输出 `[gate 3/7 单测] 通过 (9.1s)`；失败时输出红块，包含"哪一步红、命令原文、最后 20 行输出、生产未被改动"的确认，并提示 `GATE_SKIP=1` 的存在与代价。
- `docker:audit`：无漂移时输出"未发现漂移，未做任何修改"，退出码 0；有漂移时输出漂移项清单（表、判定键、差异数）并退出非 0。禁止把"无事可做"渲染成失败。

## ④ DoD 验收标准

1. 连续执行 3 次 `docker:backup`：产出 3 份完整快照，磁盘增量 < 单份全量的 30%（硬链接生效）；保留 10 份的裁剪逻辑用临时调低 `BACKUP_KEEP=2` 验证过一次。**已实测**：3 次备份分别为 69M / 316K / 316K，备份根目录合计 70M（第二三次新增占用 <0.5%）；`BACKUP_KEEP` 裁剪逻辑待用低值验证一次。
2. `docker:backup:verify` 输出逐表比对：`contents`/`publish_records`/`video_metrics`/`import_row`/`cet_words` 行数与业务键集合差异为 0；执行后测试实例 `show databases` 无 `lf_backup_check` 残留。
3. 故意破坏演练：两种破坏都必须被抓到。**已实测**——
   - 删 1 行 `publish_records`：报"行数差异（差 -1 行）"，44 → 43；
   - 只改 `upload_marks.platform`（行数不变）：报"键集合差异"，键校验和 92923876155 → 93043732818；
   - `backup:verify` 真实退出码 = 1（不经管道取码）。
   过程中还抓到**校验脚本自己的一次假通过**：`import_row` 的比对 SQL 因 `row_number` 是 MySQL 8 保留字报 1064 语法错，脚本拿到空值却把两边的空判成"一致"。已改为：SQL 失败即红灯并打印错误原文，行数非纯数字即判"结果不可解析"红灯。这条是本套门禁最要紧的自证——对账工具自己骗人比对账缺失更危险。
4. `docker:release` 红灯演练：注入一条孤儿发布记录使 `docker:audit` 红 → 断言 `deploy/prod.env` 的 `APP_VERSION` 未变、生产容器启动时间未变、退出码非 0；撤掉注入后重跑 → 放行。
5. `GATE_SKIP=1` 演练：跳过时日志明确列出被跳过步骤；去掉该变量后同一步仍然拦得住。
6. 不变量套件：9 条全绿；且把产品代码里"标记派生发布记录"临时改坏，第 1 条必须红（演示红→改回→绿）。无 `TEST_DATABASE_URL` 时套件 skip，且 `docker:release` 在质量段把它计为红而非通过。
7. backend `pnpm coverage` 在新阈值下通过；阈值数字与实测值的关系在配置注释里可读出（不是"目标 90"）。
8. `docker:audit` 全程零写入：执行前后生产库的 `binlog` 位置或业务行数不变（给出执行前后计数对照作为证据）。
9. 回归不劣化：`pnpm typecheck`、`pnpm test`、`pnpm openapi:check` 三项与改动前同结果（当前 600+ 例全绿）。
10. 交付报告含上述每一项的实际命令输出摘要；未做到 6/7 的项如实标注"未验证"，不得用静态检查替代。

## ⑤ 破坏性操作清单

| 操作 | 破坏性 | 处置 |
|---|---|---|
| `cmd_release` 构建并改写 `APP_VERSION` + `up -d` | 生产版本变更；容器重启会重放 up-only 迁移 | 前置备份不可跳；失败不切版本；已有 `docker:rollback <tag>` 回代码 |
| `cmd_backup` 读生产库 | 只读（`--single-transaction` 不锁表） | 无需确认；但会占用一次连接 |
| `cmd_backup` 删除超期备份 | **删文件** | 只删本命令自己产出的、命名匹配 `<前缀>-<日期>` 的目录/文件，删除前逐条打印；不使用全局 prune |
| `cmd_backup_verify` 建/删临时 schema | 在**测试实例**上建库、灌数据、DROP | DROP 前打印将被删除的库名；库名固定 `lf_backup_check` 前缀，不触碰 `language_flow` |
| `cmd_audit` | 只读 `SELECT` + 文件存在性 | 无写路径 |
| 不变量测试 | 写**测试库**，事务回滚 | 用例级 rollback；夹具可重灌 |

# 20 质量与运维门禁 需求文档

> 角色视角：高级产品经理（可交付性 / 验收口径 / 范围边界）
> 关联：`docs/21_质量与运维门禁架构设计.md`（怎么做）、`docs/18_发布数据一致性需求文档.md`（备份流程的原始出处）、`docs/19_发布数据一致性架构设计.md`
> 日期：2026-10-03

## 一、为什么现在要做

这套系统的唯一操作者是产品负责人本人，代码大量由 AI agent 产出，生产与开发跑在同一台 Mac 上。当前的质量与发布机制在三个地方与实况不符：

| 事实 | 证据 | 后果 |
|---|---|---|
| **生产数据没有任何备份/恢复路径** | 全仓无 mysqldump/restore 工具；数据只在 `mysql_data` 卷，与宿主机同一块物理盘 | 2026-09-28 已真实发生过一次：覆盖式操作把两集内容打回旧快照，事后只能靠读成片截帧反推文案恢复（见 `packages/backend/scripts/recover-publish-data.ts` 头注） |
| **"覆盖率 ≥90%"是假承诺** | 三包 `vitest.config.ts` 都写了 90 阈值，但 `pnpm test` 不带 `--coverage`，阈值从未被任何自动环节执行；backend 实测语句 80.55% / 函数 72.39% | 数字不执行 → 没人被拦；一旦有人当真，又会去写凑数测试把它刷绿 |
| **发布动作与质量状态完全解耦** | `scripts/stack.sh` 的 `cmd_release` 只检查脏工作树，然后构建 → 改 `APP_VERSION` → `up -d`；而生产容器启动即自动执行 up-only 迁移 | 一次坏发布 = 代码不可复现地回滚（镜像可回滚），但 schema 与数据**不可回滚**（无 down、无快照） |
| 单测不验数据行为 | backend 路由测试用 mock 的 drizzle 链式对象，`upload-marks.test.ts` 自己注明 `db.transaction` 是替身、真实回滚不在单测内 | 恰恰是本项目反复出问题的层面（发布记录派生、级联删除、列表总数对账）没有守护 |
| ~~E2E 层现在不可信（"27 例中 9 失败"）~~ **已否证** | 该数字取自 2026-10-03 01:30 前后的一次 `pnpm e2e`；`pnpm docker:test` 重建 + `pnpm docker:test:seed` 重灌夹具后复跑为 **22 passed / 1 skipped / 0 failed（11.7s）**，9 个失败不复现，归因是测量打在重建前的旧 `language-flow-test-*` 镜像上 | **套件不是红的**，而且 22 例只要 12 秒——发布门禁因此可以直接跑整套默认 E2E，不必挑"冒烟子集"。真正被这次乌龙暴露的问题是：同一份代码在旧镜像上能测出完全相反的结论，**假红与假绿同源**，所以"验证必须打在新鲜产物上"要写进命令而不是靠人记得 |

**主要矛盾不是"测试不够多"，是"该拦人的地方一个都没拦住"。** 全仓 595 例单测（后端 493 + 前端 99 + 共享 3）约 10 秒跑完且全绿，却照样发生了数据丢失——因为丢数据是运维事故，不是逻辑 bug。

## 二、用户故事

唯一用户 = 产品负责人本人；执行者 = 开发会话里的 agent。

- **US-1 回得去**：作为操作者，我在做任何可能改动生产数据的动作之前，要有一条命令能产出"确定能恢复回去"的备份，并且我能亲眼验证它真的能恢复。
- **US-2 上得放心**：作为操作者，我按 `docker:release` 时，希望它在我没注意到的时候替我把关：坏了就不切版本，而不是让我事后发现生产 502 或数据飘了。
- **US-3 拦得住漂移**：作为操作者，我希望"上传标记即派生发布记录""删除内容级联清理""列表总数不丢行"这些已经修过的东西，有一份会在真数据库上跑的检查，改坏了会在上线前变红。
- **US-4 不背假指标**：作为操作者，我宁可要一个 78% 且真的会拦住我的门槛，也不要一个 90% 且永远不执行的数字。

## 三、能力矩阵（现状 → 目标）

| 能力 | 现状 | 本轮目标 | 不做什么 |
|---|---|---|---|
| 生产库备份 | 无（`docs/18` 里有一段手工命令，供一次性修复用） | 一条命令产出，含 DB dump + 成片目录，带校验和与保留策略 | 不做异地/云备份 |
| 恢复可信度 | 无人验证 | 备份后立即演一次真恢复（临时库、业务键比对、用完清理） | 不做定时任务（本机无常驻调度需求） |
| 发布前把关 | 只查脏工作树 | 备份 → 类型 → 单测 → 覆盖率 → 真库不变量 → E2E 冒烟 → 生产只读对账，任一红不切版本 | 不引入 CI、不把 E2E 塞进 git hooks |
| 数据不变量守护 | 真库集成测试默认 skip，且指引写错端口 | 常驻的不变量测试套件，跑在测试库，改坏即红 | 不追求覆盖所有 service |
| 覆盖率承诺 | 写 90、跑不到、达不到 | 阈值改为实测水位并真正接入发布门禁 | 不为凑数写测试 |

## 四、验收标准（量化）

本轮交付需同时满足：

1. `pnpm docker:backup` 产出备份包（DB dump + uploads 快照 + `.sha256`），命令输出包含：文件路径、大小、完整性校验结果、**恢复演练逐表行数比对表**，且比对以业务键为准（自增 id 不参与比对）。
2. 恢复演练结束后临时库被清理，`docker exec language-flow-test-mysql mysql -e "show databases"` 中不残留演练库；备份目录中不残留半成品文件。
3. 连做 N 次备份，磁盘增量远小于 N 倍全量（成片快照用硬链接式增量），且始终只保留最近 10 份。
4. 人为制造一个红灯（例如临时改坏一条不变量断言指向的产品代码，或注入一条孤儿发布记录）后执行 `pnpm docker:release`：**`deploy/prod.env` 的 `APP_VERSION` 不变，生产容器不重启**，命令以非 0 退出并指出红在哪一步。
5. 显式跳过（`GATE_SKIP=1`）时：日志用醒目段落列出"被跳过的是哪几步、由谁跳过"，且**备份步骤不在可跳过范围内**。
6. backend 覆盖率阈值改为 78/82/70/78（语句/分支/函数/行），并在发布门禁里真正执行一次；三包 `vitest.config.ts` 的注释写明"这是实测水位下沿，不是目标值"。
7. 真库不变量测试 ≥6 条，在测试库跑，能捕获故意注入的破坏（演示一次红→修好→绿）；跑完不污染 `docker/test-fixtures` 的夹具数据（用事务回滚）。
8. `pnpm docker:audit`（生产只读对账）全程只有 `SELECT`，输出漂移清单；不漂移时明确说"无事可做"，不得报成失败。
9. 交付报告附实际执行记录（命令 + 输出摘要），不接受"typecheck 通过"这类静态检查作为功能验证证据。

## 五、范围边界

**本轮包含**：备份与恢复演练命令、发布门禁、真库不变量测试、生产只读对账、覆盖率阈值口径修正、`docs/12` 与 `PROGRESS.md` 同步。

**本轮明确不做**（评估过但按 ROI 砍掉）：

- 加 CI / 服务端流水线。2026-08-29 已有决策去除 GitHub Actions，单人单机无第三方审核人，收益≈0。
- 新开分支自动跑测试。分支是 agent 的工作隔离单位，不是质量单位；全量单测 9 秒，本就该全跑。
- 变异测试、按改动选用例、把 E2E 进 hooks。
- 给 16 个 view / 23 个组件补前端单测（归属 E2E，两套守同一件事是负债）。
- 把 backend 覆盖率补到 90%（`analytics-import-batch.service.ts` 单文件 1017 句未覆盖，工作量远超本轮三件事总和）。

## 二、三轨环境（版本双轨：test 跑工作树，生产跑固定 tag）

| 入口 | 界面 | 代码版本 | 数据源 | 用途 |
|------|------|----------|--------|------|
| `pnpm dev` | 5173（本地热更新） | 当前工作树 | 测试栈 MySQL :3307 + ~/language-flow-uploads-test | 日常开发，永不碰生产数据 |
| `pnpm docker:test` | 5174（nginx 同源反代） | 当前工作树（每次 --build） | 测试栈自有库（fixture 预置，`docker:test:seed` 可重灌） | 开发/测试验收，全栈形态 |
| `pnpm docker:up` | **15173**（容器） | **deploy/prod.env 的 APP_VERSION 固定 tag** | 生产库 language-flow-mysql + ~/language-flow-uploads | 老版本常驻正式使用 |

> **访问不上 ≠ 故障（先分清常驻轨与临时轨）**：5174 / 15173 是 Docker 容器，`up` 后常驻在线；
> **5173 与宿主 8080 是本地 dev 前台进程，仅 `pnpm dev` 运行期间存在**（Ctrl+C / 终端关 / 验收完清理即停）。
> 因此 5173 报 `ERR_CONNECTION_REFUSED` 多为正常（dev 没开），不是服务坏了：想用重新 `pnpm dev`，
> 否则用常驻的 5174 看最新代码。一句话：**5174=最新且常驻；5173=dev 开着才在；15173=旧版生产不随工作树变。**

> **版本双轨模型**（2026-09-21）：`docker-compose.yml` 已去掉 `build:` 段，生产只跑打了版本 tag 的镜像
> （tag = `v<git SHA>`）。工作树怎么改、测试栈怎么重建，生产都不动；只有显式 `pnpm docker:release`
> 才切换生产版本，`pnpm docker:rollback <tag>` 改回旧 tag 即回滚（数据层 `mysql_data` 卷 +
> `~/language-flow-uploads` 始终不随版本变动）。版本与端口参数集中在 `deploy/prod.env`（入仓）。

> **端口零重叠 = 三轨可并行跑**：生产 UI 已从 5173 改到 `127.0.0.1:15173`，且后端不再映射宿主 8080
> （API 只经 frontend nginx 同源反代）。此前两者与本地 dev 完全重叠，实测会串台：浏览器对 `localhost`
> 的 IPv4/IPv6 双解析 + 没关的老标签页，会把新 UI 的 `/api/dashboard/summary`、`/api/llm/status` 打到
> 老后端上 404，并快速击穿全端点共享的 100/min 限流（429），同时成片误写生产库/生产 uploads。

> **生产栈不设 `NODE_ENV=production`**（配置层关限流）：限流开启时为全端点共享 100/min，仅
> `/api/dashboard/summary` 有只读豁免（`v171d1d6` 起含）；其余高频只读页面操作仍可能触发 429，
> 维持不设。注意重启容器只能清零 60s 窗口，不解决此问题。

> 设计说明（承前）：本地 dev 的 `DATABASE_URL`/`UPLOADS_DIR` 由 stack.sh 以进程环境变量注入（优先于 .env），
> `.env` 本身保持生产连接串不变；`pnpm --filter backend dev|db:*` 脚本内置 `:-` 默认值兼底到测试库 :3307，
> 绕过 stack.sh 直跑也不会默连生产库（Node 的 `--env-file` 不覆盖已导出的真实 env）。

| 命令 | 作用 |
|------|------|
| `pnpm dev` | 释放本仓 dev 端口（只杀本仓进程，绝不动 OrbStack）→ 拉起测试栈 MySQL → 本地前后端；**不再停生产容器** |
| `pnpm docker:test` | 构建并启动测试栈（5174），代码 = 当前工作树 |
| `pnpm docker:up` | 校准生产 MySQL → `compose up -d`（**不构建**，用 APP_VERSION 指向的镜像） |
| `pnpm docker:release [tag]` | 发布：工作树 → 构建 → 打 `v<git SHA>` tag → 改 APP_VERSION → `up -d`（脏工作树需 `FORCE=1`） |
| `pnpm docker:rollback <tag>` | 回滚：APP_VERSION 改回旧 tag 并重启（本地无该 tag 则拒绝） |
| `pnpm docker:version` | 三轨当前版本/镜像/构建时间一览 |
| `pnpm docker:rebuild` | 无缓存重建并发布（用 `NO_CACHE=1` 走 release，同样会切生产版本） |
| `pnpm build` | 仅构建并打 tag（不切版本、不启动） |
| `pnpm docker:stop` | 停生产 backend/frontend + 释放本仓 dev 端口（**保留 MySQL**） |
| `pnpm docker:mysql` | 仅校准 MySQL（健康 + 挂上 `language-flow-ai_default`，别名 `mysql`） |

底层脚本：`scripts/stack.sh`（所有 compose 子命令已内置 `--env-file deploy/prod.env`，不要裸跑 `docker compose`）。

### 2.1 首次本地开发

```bash
pnpm install
# 配置 packages/backend/.env（从 packages/backend/.env.example 复制：DATABASE_URL / LLM_* 等）
# db:* 默认打测试库 :3307（需先 `pnpm docker:test` 或 `pnpm dev` 拉起测试栈 MySQL）
pnpm --filter backend db:migrate   # 首次或 schema 变更
pnpm --filter backend db:seed      # 词库（seed-data/cet_words.csv）
pnpm dev                           # 自动起测试栈 mysql + 生成 Three.js vendor（copy:vendor）+ 本地 5173/8080
```

> 误连生产库的双保险：`db:migrate` / `db:seed` 入口调 `requireSafeWriteTarget()`（`src/db/index.ts`），
> 目标为回环 `:3306` 且未显式 `DB_ALLOW_PROD=1` 时直接中止（服务启动仅告警，不阻断 openapi:gen）。
> 生产库的 schema 迁移由发布流程在容器 entrypoint 自动完成（容器内主机名是服务名 `mysql`，不命中护栏）。

> Three.js 片头依赖 `three@0.160.0`（npm），`renderer/vendor/` 为构建期拷贝产物、不入库；`pnpm dev` 与 Docker 构建阶段会自动执行 `pnpm --filter backend copy:vendor`。手工可跑 `pnpm --filter backend copy:vendor`。

### 2.2 启动 / 常驻生产老版本

```bash
pnpm docker:up
# 浏览器打开 http://localhost:15173（生产专用端口；5173 不再被生产占用）
pnpm docker:version   # 确认当前生产 tag 与镜像构建时间
```

不构建、不拉网、与本地 dev / 测试栈互不影响，可长期常驻。需要把当前代码变成生产版本时才跑：

```bash
git commit ...                 # 发布要求工作树 clean（否则需 FORCE=1）
pnpm docker:release            # → 构建 + 打 v<git SHA> + 切 APP_VERSION + up -d
pnpm docker:rollback v5cda142  # 随时回滚到旧 tag（旧镜像不删）
```

### 2.3 开发期间怎么跑

```bash
pnpm dev           # 不再停生产容器：三轨端口不重叠，可同时存在
```

**脚本自动处理的问题**：
- 本仓遗留的 tsx watch / vite 抢 8080/5173 → 只杀命令行包含本仓路径的进程（**绝不 kill OrbStack / docker-proxy**，否则会同机器其他项目的容器一起掉线）
- 裸容器 `mysql` 与 `language-flow-mysql` 抢 3306
- `docker start language-flow-mysql` 后未挂回 compose 网络 → backend `ENOTFOUND mysql`

**仍需手动**：确认没有在飞的渲染再保存后端文件（本地 dev 热重载会打断 `POST /api/video/render`，任务会停在 `video_rendering`）；要避开就改走测试栈 5174 渲染。

### 2.4 测试栈运维速查

```bash
pnpm docker:test        # 构建并启动测试栈（5174）
pnpm docker:test:seed   # 重灌预置测试数据（幂等，docker/test-fixtures/test-data.sql）
pnpm docker:test:stop   # 停测试栈（数据卷保留）
docker exec -it language-flow-test-mysql mysql -udev -pdev language_flow  # 直连测试库
```
独立卷 `language-flow-test_mysql_test_data`，与生产卷 `language-flow-ai_mysql_data` 互不可见；测试栈 MySQL 另映射 127.0.0.1:3307 供本地 dev 连接。

> **监听边界（2026-09-26 审查批次 2A）**：测试栈 UI 映射改 `127.0.0.1:5174:80`、生产栈 MySQL 改 `127.0.0.1:3306:3306`——零认证面/数据库均不无意暴露到局域网；如需手机等其他设备验收测试栈 UI，临时改回 `"5174:80"` 用完还原。nginx 已为全部响应加 `X-Content-Type-Options/X-Frame-Options/Referrer-Policy` 基础安全头。

预置测试数据由 `docker/gen-fixture.py` 生成（真实词数 8-12，与生成链路约束一致），改数据口径改脚本重生成即可。

**注意**：三轨不再互斥（dev 5173/8080 · 测试栈 5174/3307 · 生产 15173），但遗留的 tsx watch 父进程仍会抢 dev 端口——重开终端前用 `lsof -iTCP:8080 -sTCP:LISTEN` 确认只有一个监听者。另：测试栈与本地 dev **共用**测试栈 MySQL（:3307）与 `~/language-flow-uploads-test`，不要在两边同时对同一内容点渲染。

## 六、Docker 容器化部署（生产栈 = 固定 tag，不随工作树变）

```bash
pnpm docker:up
# 内部：校准 MySQL 网络 → docker compose --env-file deploy/prod.env up -d（不构建、不拉取）
```

| 服务 | 容器名 | 访问地址 | 说明 |
|------|--------|----------|------|
| frontend | language-flow-frontend | http://localhost:15173 | nginx；反代 /api、/files、/doc、/health |
| backend | language-flow-backend | 不映射宿主端口 | Hono API + TTS + 视频渲染（只能经 nginx 访问） |
| mysql | language-flow-mysql | 127.0.0.1:3306 | 固定网络 `language-flow-ai_default`，别名 `mysql`；宿主映射仅绑回环（批次 2A） |

镜像版本由 `deploy/prod.env` 控制（入仓，就是“生产现在跑哪个版本”的唯一凭据）：

| 变量 | 当前值 | 说明 |
|------|--------|------|
| APP_VERSION | `v5cda142` | 生产 backend/frontend 镜像 tag（= 发布时的 git SHA）；改它 + `up -d` 即发布/回滚 |
| PROD_UI_PORT | 15173 | 生产 UI 宿主端口（与 dev 5173 / 测试栈 5174 不重叠） |

启动行为（entrypoint.sh）：

1. 等待 MySQL 就绪（healthcheck）
2. `tsx src/db/migrate.ts` — 应用 drizzle 迁移（幂等）
3. `tsx src/db/seed.ts` — 词库 seed（幂等）
4. 启动后端

**禁止**单独 `docker start language-flow-mysql`（易掉网 → backend `ENOTFOUND` → 前端 502）。请用 `pnpm docker:mysql` / `pnpm docker:up` / `pnpm dev`。

### 环境变量（docker-compose.yml 可覆盖）

| 变量 | 默认值 | 说明 |
|------|--------|------|
| LLM_BASE_URL | http://host.docker.internal:11434/v1 | Ollama 默认连宿主机（macOS/Linux extra_hosts 已配 host-gateway） |
| LLM_API_KEY | ollama | Ollama 不校验 |
| LLM_MODEL | qwen2.5:7b | 模型名 |
| CORS_ORIGIN | http://localhost:5173 | CORS |
| LOG_LEVEL | info | pino 日志级别 |

### 数据与文件

- 数据库：`mysql_data` 卷（可改用外部卷：`external: true`）
- 上传文件（audio/video/bgm）：生产栈绑定挂载 `${HOME}/language-flow-uploads` → 容器内 `/app/packages/backend/uploads`；Docker 测试栈挂 `${HOME}/language-flow-uploads-test`；本地 dev 由 `UPLOADS_DIR` 直指测试目录（与生产文件资产隔离）
- Finder 定位桥：`POST /api/files/reveal` 写 `<uploads>/.open-requests/<ts>-<file>.req`（内容 = 宿主机绝对路径），
  宿主机 launchd 脚本 `scripts/reveal-watcher.sh` 扫 `~/language-flow-uploads*/.open-requests` 后 `open -R`（glob 一次覆盖三轨，目录命名必须遵守 `language-flow-uploads*` 约定）
- 前端同源部署：构建时 `VITE_API_BASE_URL=""`，所有请求走 nginx 代理

### 镜像与构建说明

- `Dockerfile.backend`：node:24-bookworm-slim + ffmpeg + fonts-noto-cjk（中文渲染）+ Chromium（npmmirror 下载，`PLAYWRIGHT_DOWNLOAD_HOST` 可覆盖）
- `Dockerfile.frontend`：node 构建（gen-api 生成 schema.d.ts → vite build）→ nginx:alpine
- 首次构建需拉取基础镜像；Docker Hub 不通时已在 OrbStack 配置 registry-mirrors（daocloud / hub.rat.dev）
- **构建时机**：日常开发用 `pnpm dev`（或 `pnpm docker:test` 跑全栈形态）；生产只在 `pnpm docker:release` 时构建，旧 tag 不删 → 可回滚

### 常见问题（容器化）

| 问题 | 处理 |
|------|------|
| 502 / `ENOTFOUND mysql` | `pnpm docker:mysql` 或 `pnpm docker:up`；勿手搓 `docker start` MySQL |
| 生产页面 429 | 该版本无只读端点限流豁免：确认生产 compose 未设 `NODE_ENV=production`；重启容器只清零 60s 窗口，不根治 |
| 新 UI 标签页打到生产老后端（404） | 三轨端口已不重叠；出现 404 先确认地址栏是 15173/5174/5173 中的哪一个，并关掉旧标签 |
| 本地 dev 视频写到了生产 uploads | 该进程 `UPLOADS_DIR` 没注入（遗留 watcher）；杀掉全部 tsx watch 后重跑 `pnpm dev`（脚本会导出三个变量） |
| 「在 Finder 中显示」无反应 | 改过 `scripts/reveal-watcher.sh` 需 reload：`launchctl unload ~/Library/LaunchAgents/com.languageflow.reveal-videos.plist && launchctl load ~/Library/LaunchAgents/com.languageflow.reveal-videos.plist`（KeepAlive 会自动换新逻辑） |
| 冲突容器名 `mysql` 占 3306 | 脚本会自动 `docker stop mysql`；请只用 `language-flow-mysql` |
| 旧库数据迁移 | `mysqldump` → 导入；无 drizzle 迁移表时先 baseline |

## 七、生产部署方向（规划）

| 组件 | 方案 |
|------|------|
| 后端 | Node 24 服务（`pnpm --filter backend build` → `node dist/index.js`），反向代理 Nginx/Caddy |
| 数据库 | MySQL 8.4（云 RDS 或自建），DATABASE_URL 指向生产库 |
| 前端 | `pnpm --filter frontend build` → 静态文件托管（Nginx/CDN），API 地址走环境变量 |
| 文件存储 | MVP：`uploads/` 本地盘 + Nginx 静态路由；生产化：S3 兼容对象存储（SPEC 已预留） |
| 视频渲染 | 部署机安装 Chromium（`playwright install chromium --with-deps`）+ ffmpeg |
| 日志 | pino 结构化日志 → stdout 采集（如 Loki/CloudWatch） |
| 反向代理 | /api → backend:8080；/files → uploads 静态；/ → frontend 静态 |

### 生产部署待办（接入时执行）

1. 确定服务器与域名，配置反向代理
2. 生产数据库初始化（db:migrate + db:seed 词库）
3. 设置 `NODE_ENV=production`、CORS_ORIGIN、密钥类环境变量（注意：先确认目标版本的限流豁免已覆盖高频只读轮询端点，否则开着会 429）
4. 服务器侧构建或拉取构建产物（本仓库不启用 CI 自动上传）

## 八、常见问题（FAQ）

| 问题 | 处理 |
|------|------|
| `Access denied for user 'dev'` | 容器非本仓库 compose 启动，按 §二 补建用户 |
| `DATABASE_URL is not set` | pnpm 脚本不加载 .env，命令前显式 `DATABASE_URL=...` |
| 3306 端口占用 | `docker ps` 查看已有容器，或改 compose 端口映射 |
| 健康检查 404 | 正确路径是 `GET /health`（挂在 `/` 下），不是 `/api/health` |
| Chromium 启动失败（#18 后） | `pnpm --filter backend exec playwright install chromium` |

## 更新记录（2026-09-21：版本双轨 + 端口零重叠）

背景：生产栈与本地 dev 共用 5173/8080，导致新 UI 标签页打到老后端（404 + 限流击穿）、成片误写生产库，且 `pnpm dev` 会停掉生产容器。

- **生产栈不再从工作树构建**：`docker-compose.yml` 去掉 `build:` 段，改用 `image: ${APP_VERSION}`；版本与端口入 `deploy/prod.env`（`APP_VERSION=v5cda142`、`PROD_UI_PORT=15173`）
- **发布/回滚入命令面**：`pnpm docker:release`（构建→打 `v<git SHA>`→切 APP_VERSION→up -d，脏工作树需 `FORCE=1`）、`pnpm docker:rollback <tag>`、`pnpm docker:version`；`docker:up` 不再构建
- **端口解耦**：生产 UI → `127.0.0.1:15173`，后端不映射宿主 8080（只走 nginx 同源反代）；三轨 dev(5173/8080) · 测试栈(5174/3307) · 生产(15173) 可并行常驻，`pnpm dev` 不再停生产容器
- **端口释放不再误杀基础设施**：`stack.sh` 只杀命令行包含仓路径的进程（之前会 `kill` 到 OrbStack 主进程，连带影响同机器其他项目的容器）
- **生产栈关限流（配置层）**：去掉 `NODE_ENV: production`（当前生产 tag 无只读端点豁免，开着必 429）
- **防误连生产库**：`pnpm --filter backend dev|db:*|openapi:gen` 内置 `:-` 默认值指测试库 :3307（与 `.env` 的生产连接串解耦）；`db:migrate`/`db:seed` 入口新增 `requireSafeWriteTarget()` 护栏，回环 :3306 需 `DB_ALLOW_PROD=1` 才写（容器内服务名 `mysql` 不受影响）
- **文档同步**：本文 §二/§三/§六、AGENTS.md §零（端口与常用命令）、README 部署段
- **Finder 定位桥修复**：`reveal-watcher.sh` 原本只扫硬编码的生产 uploads 目录 → Docker 测试栈与本地 dev 的「在 Finder 中显示」写了 `.req` 永远没人消费（注入 `HOST_UPLOADS_DIR` 后本地 dev 也走这条桥）；改为扫 `~/language-flow-uploads*/.open-requests`（glob 一次覆盖三轨，容忍 `$HOME` 含空格），并补上目标缺失时的 60s 宽限期丢弃（不再无限重试堆积）

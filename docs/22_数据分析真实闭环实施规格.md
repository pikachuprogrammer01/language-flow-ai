# 数据分析真实闭环实施规格

> 版本：V1.0  
> 状态：已确认，待分批实现  
> 来源：用户确认的“全选 A”方案；与 `docs/17_视频数据分析模块设计.md`、`SPEC.md`、`docs/19_发布数据一致性架构设计.md` 配套使用。  
> 目标：让 coding agent 可以按批次直接实施、验证和交付，不需要重新做产品决策。

## 1. 已确认的产品决策

1. 视频表现列表以本地内容为主实体，一条已生成内容一行；发布记录和指标作为平台明细。
2. 未发布的本地成片也要出现在统一列表中，但不创建虚假的 `local` 发布记录。
3. 生产和开发页面不提供假分析数据；测试夹具只能存在于隔离测试环境。
4. 多平台指标默认不跨平台相加；平台口径不同，必须按平台查看。
5. 因子分析默认目标为 `completion_rate`；缺失时提示用户切换 `effective_play_rate_2s`。
6. 可执行参数建议要求同平台、同窗口、同指标至少 8 个非空真实样本；估算值不计入行动门槛。
7. 推荐只作用于当前生成链路已有参数，用户点击后预填，最终值以用户提交为准。
8. 推荐必须保留“建议→采纳→实际生成参数→发布→导入指标”的完整链路。
9. 内容实验在生成时显式选择 A/B 变体，不做隐式随机。
10. 实验评估使用真实导入指标；每个变体样本不足 8 时只展示观察，不宣布胜者或因果结论。
11. 新建发布记录的默认发布时间取 `contents.created_at`。
12. 历史空发布时间只回填空值；导入和人工填写的已有时间不得覆盖。
13. 发布时间来源记录为 `LOCAL_GENERATED`、`PLATFORM_IMPORTED`、`USER_EDITED`；无法判断的旧非空记录允许来源为空。
14. 保留现有已发布 API 契约；统一内容主视图使用新增接口。
15. 本批不做模型权重训练、自动修改全局默认参数、SHAP 或在线随机策略；先沉淀真实反馈数据。

## 2. 当前基线和问题边界

当前 `/api/analytics/videos` 以 `publish_records` 为行锚点，本地有成片但没有发布记录的内容只通过 `unregisteredContentCount` 暴露；这导致分析页不能完整呈现本地生产资产。因子分析、推荐和实验已有基础实现，但推荐采纳只保留有限回写，实验主要依赖手工选择已有内容。发布记录创建时 `publishTime` 默认为 `NULL`，数据接入页因此显示 `-`。

现有事实必须继续遵守：

- 外部绩效数据唯一入口是四步导入链路，禁止绕过 `import_batch/import_row/match_candidate/match_decision` 直接写指标。
- 指标必须使用 canonical 名称并携带 provenance；缺失值不能补成 0。
- `publish_records` 是外部发布关系；`upload_marks` 保持发布管理契约，不与新模型混写。
- `ContentDTO` 14 个核心字段、状态流转和已有 API 路径/请求/响应结构不得破坏。
- Phase 5 模型训练保持待启动状态，当前只做可解释分组统计和描述性实验。

## 3. 目标数据流和不变量

```text
contents（本地生成事实）
   ├─ content_features（生产参数和字段来源）
   ├─ publish_records（平台发布关系）
   │    ├─ video_metrics（最新指标 + provenance）
   │    ├─ video_metric_daily（每日快照）
   │    └─ import_batch/import_row（导入批次和原始行）
   └─ experiment_assignments（实验变体归属）

video_metrics + content_features
   → analysis_result（目标指标和分组统计快照）
   → recommendations（可执行建议）
   → recommendation_applications（采纳和最终参数）
   → 新内容
```

必须满足以下不变量：

- 统一内容列表以 `contents` 为根，只有真实视频产物才默认进入列表；没有发布记录时 `platforms=[]`，状态为 `unpublished`。
- 一个内容可以有多个平台发布记录；一个平台发布记录只能属于一个内容。
- 主行不得把不同平台的播放、点赞、完播或互动计数相加。
- 导入指标必须能通过 `metadata.batch_id`、`import_row` 和 `source_field` 找到原始来源。
- 生产事实来自 `contents`/`content_features`/audit，不得由 LLM 猜测已知事实。
- 因子建议低于门槛时只能产生 `data_readiness`，不能产生参数改变建议。
- 推荐采纳不改变历史指标，只记录用户最终实际使用的参数。
- 实验归属独立存储，不向 `ContentDTO` 增加字段。

## 4. 数据库变更

### 4.1 `publish_records`

新增可空枚举列：

```text
publish_time_source ENUM('LOCAL_GENERATED','PLATFORM_IMPORTED','USER_EDITED') NULL
```

写入规则：

| 场景 | `publish_time` | `publish_time_source` |
|---|---|---|
| 新建发布记录，未提供时间 | `contents.created_at` | `LOCAL_GENERATED` |
| 新建/更新时提供外部平台时间 | 外部时间 | `PLATFORM_IMPORTED` |
| 用户在发布记录表单中编辑时间 | 表单时间 | `USER_EDITED` |
| 历史记录已有非空时间但来源无法判定 | 保留原值 | `NULL` |
| 历史记录时间为空 | 关联内容 `created_at` | `LOCAL_GENERATED` |

导入提交只有在导入行包含真实发布时间时才更新发布记录；没有发布时间的导入行不得清空已有值。

### 4.2 `recommendation_applications`

新增关系表，保存推荐采纳的可审计链路：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `recommendation_id` | FK → `recommendations.id` |
| `content_id` | 生成成功后绑定的内容 ID，可空 |
| `suggested_params` | 推荐值 JSON |
| `prefill_params` | 页面预填值 JSON |
| `final_params` | 用户最终提交给生成链路的值 JSON |
| `target_metric` | 该推荐针对的 canonical 指标 |
| `analysis_result_id` | 生成该建议的快照，可空 |
| `accepted_at` | 用户点击使用推荐的时间 |
| `applied_at` | 成功绑定内容的时间，可空 |
| `created_at` / `updated_at` | 自动维护 |

不得把这张表的字段复制进 ContentDTO 核心字段。

### 4.3 `experiment_assignments`

新增关系表：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `experiment_id` | FK → `experiments.id` |
| `content_id` | 绑定后填写，允许创建前为空 |
| `variant` | `A` 或 `B` |
| `assignment_method` | 第一版固定为 `operator_selected` |
| `assigned_params` | 分配时实际参数 JSON |
| `final_params` | 生成提交时最终参数 JSON |
| `assigned_at` | 分配时间 |
| `bound_at` | 内容生成成功绑定时间，可空 |
| `created_at` / `updated_at` | 自动维护 |

已有 `experiments.variantA/variantB.contentIds` 继续兼容读取；新流程以 `experiment_assignments` 为事实来源，评估时动态得到两组内容。

### 4.4 迁移规则

- 使用新的增量 migration，不重写已经发布的 migration。
- 迁移前只允许连接测试库 `:3307` 演练；禁止为方便而写生产库。
- 回填脚本必须先 dry-run，输出空时间记录数、可回填数和冲突数。
- 回填只更新 `publish_time IS NULL` 的记录，并通过 `content_id` 关联 `contents.created_at`。

## 5. API 设计

### 5.1 新增统一内容主视图

新增：`GET /api/analytics/content-videos`

查询参数：

```text
status: all | unpublished | published_unimported | imported | import_conflict | failed | deleted
platform: string，可选
sort: created_time | publish_time | play | completion | engagement
order: asc | desc
page: >=1，默认 1
pageSize: 1..100，默认 20
```

响应：

```json
{
  "items": [
    {
      "contentId": "...",
      "title": "...",
      "template": "scene_word",
      "level": "CET4",
      "localStatus": "ready",
      "generatedAt": "2026-10-04T08:00:00.000Z",
      "videoAssetId": "...mp4",
      "durationSec": 32.4,
      "platformCount": 1,
      "metricCoverage": { "platforms": 1, "records": 1, "recordsWithMetrics": 1 },
      "platforms": [
        {
          "recordId": "...",
          "platform": "抖音",
          "platformVideoId": "...",
          "publishStatus": "published",
          "publishTime": "2026-10-04T08:00:00.000Z",
          "publishTimeSource": "LOCAL_GENERATED",
          "metrics": {
            "play_count": {
              "value": 1200,
              "sourceType": "CREATOR_IMPORT",
              "isEstimated": false,
              "dataDate": "2026-10-04"
            }
          }
        }
      ]
    }
  ],
  "total": 0,
  "page": 1,
  "pageSize": 20
}
```

约束：

- 旧 `/api/analytics/videos` 不修改路径、请求和响应结构。
- `metrics` 缺失键表示无数据，不能返回 0。
- 主行不提供跨平台合计指标；平台指标只能在 `platforms[]` 中读取。
- `generatedAt` 来自 `contents.createdAt`，不冒充平台发布时间。

### 5.2 推荐证据

新增：`GET /api/analytics/recommendations/{recommendationId}/evidence`

返回：目标指标、平台、时间窗口、`analysisResultId`、分组维度、每组样本数/中位数/均值、参与的 `recordId`、指标 provenance、`batchId`、原始行号、生产特征字段来源和审计路径。

找不到推荐或快照返回 404；证据缺失时返回明确 `evidence_unavailable`，不得拼接猜测内容。

### 5.3 实验分配与绑定

新增：

```text
POST /api/analytics/experiments/{experimentId}/assignments
POST /api/analytics/experiments/{experimentId}/assignments/{assignmentId}/bind
```

分配请求：

```json
{ "variant": "A", "assignedParams": { "template": "scene_word" } }
```

绑定请求：

```json
{ "contentId": "...", "finalParams": { "template": "scene_word" } }
```

只有实验 `draft` 或 `running` 状态允许分配；变体只能是 `A/B`；绑定必须引用真实生成成功的内容。原实验接口继续可读，评估优先使用 assignments。

## 6. 因子与推荐规则

### 6.1 因子查询

- 页面默认 `targetMetric=completion_rate`。
- 若目标指标没有可用样本，页面明确提示切换 `effective_play_rate_2s`。
- 分组维度继续使用 `analytics-taxonomy.ts` 白名单。
- 统计只使用同一平台、同一时间窗口、同一 canonical 指标的非空值。
- 每组必须显示样本数、覆盖数、来源类型和“相关性非因果”声明。

### 6.2 推荐生成

推荐生成服务必须返回以下两类之一：

1. `actionable`：样本数 ≥ 8，存在可比较组，给出目标参数、建议值、当前基线、差异、样本数和置信度。
2. `data_readiness`：样本不足、指标缺失、跨平台混合或来源不可追溯，给出需要补充的数据，不给参数改动结论。

生成建议时不得：

- 把估算涨粉当成真实因果证据；
- 把多个目标指标合成为黑盒评分；
- 把跨平台值直接合并；
- 把相关性写成“导致”“保证提升”；
- 修改历史指标或历史内容参数。

导入批次成功提交后，在事务完成后触发一次推荐刷新。刷新失败不回滚已提交的导入，但必须记录失败日志并保留手动重算入口。

## 7. 前端行为

### 7.1 视频表现列表

- 页面改用 `content-videos` 客户端接口。
- 默认显示本地已完成成片；支持状态、平台、排序和分页筛选。
- 未发布行显示“未发布”，发布但无指标显示“已发布，等待导入”，有指标显示来源标签。
- 平台明细展开显示 `publishTimeSource`、指标来源、数据日期和估算标记。
- 不显示硬编码指标、假增长曲线或默认 0%。

### 7.2 因子分析和推荐

- 目标指标切换后重新请求分析和推荐。
- 推荐卡必须显示：目标指标、样本数、时间窗口、平台、依据维度、来源入口。
- “使用推荐参数创建”创建 `recommendation_application`，把建议值预填到新建页。
- 用户修改参数后，生成成功时写入最终参数；失败时保留采纳记录但不绑定内容。

### 7.3 内容实验

- 新建页增加可选实验和 A/B 变体选择。
- 选择变体后先创建 assignment，再开始已有生成流程。
- 生成成功后绑定内容和最终参数；生成失败保留未绑定 assignment。
- 实验页展示真实分组统计、覆盖率、低样本状态和非因果说明。

## 8. 分批实施顺序

### 批次一：真实内容视图与发布时间

实现数据库迁移、发布时间默认/回填、内容主视图查询/API、前端表现列表切换和导入时间覆盖规则。

完成条件：本地成片全部可见；未发布不造平台记录；已有发布记录不丢；历史空时间不再显示 `-`；旧 `/videos` 契约测试不变。

### 批次二：推荐与证据链

实现推荐采纳表、证据接口、导入后自动刷新、目标指标/样本门槛、创建页最终参数记录和推荐来源展示。

完成条件：每条 actionable 建议都能追到原始导入行和生产参数；低样本只产生 data readiness；采纳后的最终参数可回放。

### 批次三：实验分配与评估

实现 assignments 表、分配/绑定接口、新建页实验选择、实验评估改读 assignments、低样本和非因果验收。

完成条件：创建实验→选择变体→生成→绑定→发布→导入→评估全链路可追溯。

每个批次按仓库单次修改范围拆成可审查的小提交；不得一次性混入生产发布、无关重构或模型训练。

## 9. 验证门禁

每批至少执行：

```bash
pnpm typecheck
pnpm lint
pnpm test
pnpm openapi:check
```

涉及页面和真实数据链路时：

```bash
pnpm docker:test
pnpm e2e
```

必须新增或修改：

- 统一内容列表服务/API 测试：左连接、状态、分页、多平台不相加、无数据不补 0。
- 发布时间测试：新建默认、历史回填、导入覆盖、人工覆盖、空导入不覆盖。
- 推荐测试：样本门槛、目标指标、证据链、刷新失败不回滚导入、最终参数留痕。
- 实验测试：变体分配、绑定、评估、低样本和无指标场景。
- E2E：真实测试库中生成内容、发布绑定、指标导入、推荐采纳和实验评估。

生产数据相关动作仍须遵守 `docker:backup`、恢复演练和七步门禁；本规格不授权生产发布或生产写库。

## 11. 批次一实施记录与偏差（2026-10-04 编码后回填）

只记与本规格**不一致**或规格未覆盖、实现时必须自行定口径的部分；未列出的按 §4/§5/§7 原样落地。

| 项 | 落地口径 | 为什么偏离/补充 |
|---|---|---|
| `publish_time_source` 不出现在 `GET /publish-records` | 来源只在 `/content-videos` 的平台明细里返回 | 硬约束「不修改已有 API 响应体结构」优先于 §4.1 表格的展示含义；`routes/analytics.test.ts` 用 zod `.strict()` 钉住旧响应字段集，将来加字段必红 |
| 上传标记派生的发布记录 | 时间与来源都是 `USER_EDITED`（标记动作即用户断言） | §4.1 的写入规则表没有「标记派生」这一行。它既不是本地生成兜底（值不是 `contents.created_at`），也不是平台导入；判给 `USER_EDITED` 是唯一不撒谎的选项 |
| `import_conflict` 判据 | 存在 `match_status='conflict'` 的导入行把该平台记录列为 `match_candidate` | §5.1 只给了状态名没给判据。冲突只活在导入中间层，因此判据从那里取，不新增冲突列、不猜 |
| 一行的状态不止一个 | 每行返回 `status`（主状态）+ `statuses`（命中全集），优先级 failed > import_conflict > deleted > imported > published_unimported > unpublished | 一行可以既有指标又有待裁决冲突；只报一个会把冲突说成没事 |
| `deleted` 的成立条件 | 该内容**全部**平台记录都是 deleted | 部分删除仍留有有效发布关系，报成 deleted 会掩盖 |
| 指标排序的聚合方式 | `sort=play/completion/engagement` 取该内容各平台该指标的 max，仅用于排序；响应里没有合计值 | §5.1 列了排序键但没说多平台时按什么排。sum/avg 会把两个平台不可比的口径混成一个不存在的数字，违反 §3 不变量 |
| 主行缺失指标的文案 | 单元格用「—」（页面 B/C 既有的无数据语汇），整段「暂无导入指标」说明每个平台只出现一次 | §7.1 要求「显示暂无数据，不显示 0」。约束的实质是不得把缺失折算成 0；9 列各刷一遍「暂无数据」会把页面刷成噪音 |
| 回填逻辑落点 | `analytics-metrics.service.backfillMissingPublishTime(apply, executor?)` + `pnpm --filter @ai-english/backend db:backfill:publish-time`（默认 dry-run，`-- --apply` 才写） | 不放进入库迁移：容器启动即 migrate，把数据回填塞进迁移等于每次发布都重写历史数据，且无法先 dry-run 看数 |
| 回滚与发布时间 | 提交写入的 `publish_time` 纳入 `commit_preimage`，回滚按旧值恢复 | §4.1 要求导入可覆盖兜底值，那么 `commit_preimage` 的回滚语义（SPEC §10.14）必须能撤销它，否则回滚后留下「已提交但没恢复」的漂移。preimage 落 JSON 列，时间以 ISO 字符串存、回滚前显式还原成 `Date`：`datetime(mode:"date")` 的 UPDATE 路径只收 Date，塞字符串会抛 `value.toISOString is not a function` 使整批回滚失败（真实 E2E 抓到过） |

**过程中修掉的第四个缺陷（既有）**：只有一组缺指标样本时，verdict 写的是「两组均无可用指标样本，无法评估」——把另一组真实存在的数据说没了。夹具实验（A 绑定 1 条 / B 绑定 0 条）真实跑评估时暴露，改为点名缺的那一组：「B 组没有可用指标样本，无法比较（无数据 ≠ 0；另一组有值也不下结论）」，并补一条纯函数用例钉住「不得写成两组都无」。分配台账的措辞同时压平（原来括号套括号读不通）。

**独立评审提出的四个问题与处置**（评审针对批次三切片，全部为真）
1. **绑定是「先查后写」**：客户端超时重发同一笔 bind 时两次都能通过前置检查，后一次静默覆盖前一次的 `contentId/finalParams`，而台账与评估文案仍说「已绑定」。改为条件更新（`WHERE bound_at IS NULL AND content_id IS NULL`）+ 回读判定：抢不到的人拿 `already-bound`，不覆盖首次事实。
2. **绑定失败后 id 被提前清空**：前端在 `await` 之前就把 `assignmentId` 置空，于是「内容已生成成功但绑定没成」这条记录永远留在未绑定里，而文案把它解释成「生成失败或未完成」——对一条真实存在的成片这是假归因。改为只在成功时清空，并把三处措辞统一成「生成失败、未完成**或绑定未成功**」。
3. **新路径比旧路径松**：`validateExperimentInput` 会拦「同一内容同时属于 A/B」，分配路径却谁都能绑，同一个视频可以进两组（自己跟自己比），且台账按行数计数、`sampleA` 按内容数，两个数字会不一致。改为 bind 时拒绝该实验台账里已存在的内容（409 `CONTENT_ALREADY_ASSIGNED`），并在装载两组时对历史脏数据去重。
4. **台账是全局单例无请求令牌**：先点 A 再点 B，A 的迟到响应会写进 B 的卡片，标题的「共 N 条 · 已绑定 M 条」用的是别人的数据。加了请求令牌，迟到响应只写回自己那次点击展开的卡片。

另修两处小的：`resetForNewVideo` 未清 `assignmentId`（新建下一条时提示条还写着「本次已登记」）；三个路由里 `z.record(z.unknown())` 已推出 `Record<string, unknown>`，多余的 `as` 去掉。

**顺着「两份数字并存必须说清哪份没被用」再补两处**
- 评估文案加一句「登记清单里的两组内容不参与本次统计」：卡片上同时显示「登记清单 A：1 条 · B：1 条」和「分配：A 已绑定 8 条」，不点破没被使用的那一份，读的人只会挑自己想信的。

**跑 `@full` 时发现的四个既有问题**（都不是本批引入，但都在「失败要说得出原因」这条线上）

- `@full` 的生成步骤本身对本地模型输出质量敏感，且**用例只等成功句，失败时要干等 10 分钟才报超时**（报出来的是 timeout，不是原因）。查了后端日志才看清两种真实终态：模型连续 3 轮过不了词库验收（「有效词不足：仅 5 个（要求至少 8 个）」/ 输出 JSON 被截断）时服务如实回 **HTTP 500**；冷启动时则先在 nginx 上撞 **HTTP 504**。同一用例实测四次：两次通过（50s / 29s）、一次 500、一次 504。
